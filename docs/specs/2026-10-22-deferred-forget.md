# 清理旧快照撞上并发备份时延后补做

> Status: Approved
> Owner: opsnap 维护者
> Last updated: 2026-10-22

**Objective:** 当同一存储位置上还有别的备份正在写、导致本次运行没法按保留规则删除过期快照时，不再把这次运行标成「有警告」并让任务长期挂在「需要处理」里，而是在存储位置空闲时自动把该做的清理补做掉。

**Hard invariant:** 不变的两条：任何失败或不完整的导出都不能记为成功的快照；撞锁只影响删除过期快照这一件事，绝不触碰本次运行刚生成的快照，也绝不删除任何人正在持有的锁。

## Problem

1. **同一存储位置上的并发备份必然让 forget 失败。** `restic backup` 取的是非独占锁，多个备份可以同时写一个仓库（`internal/pkg/cmdbuild/restic.go` 的 `ResticBackup*` 都不加独占参数）；`restic forget` 取的是独占锁，仓库上有任何其他锁就以退出码 11 结束。opsnap 默认允许 3 个任务同时运行（`max_concurrent_runs`），多个任务指向同一存储位置是常态，所以这不是偶发。
2. **实测已经发生。** 本机面板运行 5（superdog 文件，`/runs/5`）：02:49:32 执行 forget 时，运行 2 正持有 02:46:16 建的非独占锁，forget 立即退出码 11；同一时刻运行 7 也在 13 秒前的锁上失败。两次运行的快照都完整生成。
3. **良性竞争被算成「需要处理」。** `internal/service/run_svc/engine.go` 把 forget 的任何非零退出都记成 `StatusWarning`，而 `StatusWarning` 会进「需要处理」（`internal/service/run_svc/run.go` 的 `Attention`）。结果是概览、任务列表的「需要处理」被大量假问题占满，管理员分不清哪次真需要动手。
4. **原因文案不可读。** 运行详情把 restic 的整段 JSON 塞进原因，其中「`the unlock` command can be used to remove stale locks」是 restic 的通用提示；照它去点面板上的「解除仓库锁」（`unlock --remove-all`）会删掉正在运行的备份持有的锁。
5. **保留规则实际上没有生效，而且没人知道。** forget 失败后过期快照原样留着，界面上没有任何「这条任务的保留规则还没应用过」的信息。

## Actors and user stories

1. 作为**管理员**，我希望并发备份不会让运行结果变成需要处理的警告，这样「需要处理」里只剩真正要动手的事。
2. 作为**管理员**，我希望那条因为存储位置忙而没做成的清理，在存储位置空闲时自己补做，这样我不用盯着等空档。
3. 作为**管理员**，我希望看到哪些任务的保留规则还没被应用过，这样空间异常增长时我知道从哪查。
4. 作为**AI 助手或脚本**，我希望通过 API 拿到同一条「待清理」信息，这样巡检时不依赖打开面板。

## Design decisions

标记：〔用户〕用户已决定；〔核实〕已从代码核实；〔推荐〕经用户确认的推荐方案。

| # | 决策 | 依据与否决方案 |
|---|---|---|
| 1 | 保留「跑一次 forget、失败再等空闲补做」的整体形状：forget 先带 `--retry-lock 5m` 自己等一会儿，仍然撞锁就记「待清理」，由调度器在存储位置空闲时补做〔用户〕 | 单靠 `--retry-lock` 只能熬过间隙，备份不断档时照样失败；单靠补做又会让每次运行都白撞一次锁。两者叠加：多数情况下当场做完，少数情况下延后到空档。否决：只加 `--retry-lock`（`docs/specs/2026-10-15-opsnap-v1.md` 允许 3 个并发任务，永不断档是可能状态）；否决：把 forget 升级成 opsnap 内部独占锁（一次 forget 会让后续所有任务等到当前批次备份全部结束，拿吞吐换确定性，且与「维护才独占」的既有约定冲突） |
| 2 | 撞锁延后的运行记为**成功**，forget 步骤记「已跳过」，不进「需要处理」〔用户〕 | 快照完整、数据安全不变量没破，延后的只是空间回收；把良性竞争混进告警会让真正的失败消失。否决：记为「有警告」但排除出「需要处理」（状态与筛选含义对不上）；否决：记为「有警告」并保留在「需要处理」直到补做成功（持续并发备份时会长期挂着假问题） |
| 3 | 只有「仓库被锁」这一类失败才延后；forget 的其他失败仍然记「有警告」并进「需要处理」 | 密钥损坏、NAS 不可达、参数错误都不是良性竞争，延后会让真问题被掩盖。判定沿用已有先例：退出码 11 或输出含 `already locked`（`internal/service/snapshot_svc/restic.go` 已这样判定） |
| 4 | 待清理状态记在**任务**上：首次延后的时间 + 最近一次补做的失败原因。用时间戳而不是布尔值〔推荐〕 | 需要一个能显示「自某时起待清理」的锚点，时间戳与布尔值列数一样，信息更多。否决：只放内存（重启丢失，与「重启后继续」的既有行为不一致）；否决：单独的待清理表（为一个可有可无的字段建表，查询与迁移成本都更高） |
| 5 | 补做在**调度器每轮**（现有 30 秒轮询）尝试，条件是该存储位置在本进程内没有备份在写、也没有维护在进行〔推荐〕 | 复用已有的轮询与后台工作去重机制（同名工作不会并发启动第二个），不新增定时器。判定用现有的存储位置独占锁不等待获取：拿到即空闲，拿不到就等下一轮。限制：只看本进程内的并发，跨进程（例如两个 opsnap 实例指向同一仓库）不会退化为立即失败，因为 forget 自身带 `--retry-lock` |
| 6 | 补做使用**补做当下**的保留规则，而不是延后那一刻的规则 | 补做的就是「把当前规则应用到当前快照」；管理员在延后期间改了保留规则，应该按新的算。否决：记住延后时的规则（会删掉按新规则该留的快照，或留下按新规则该删的快照） |
| 7 | 已暂停的任务**也补做**〔用户〕 | 暂停只表示不再按计划产生新备份，已有快照的保留规则仍应生效，否则暂停的任务会永久占着存储位置的空间。否决：暂停即完全冻结（行为更好预测，但空间只增不减且无人察觉） |
| 8 | 一次补做的成果**不写进运行记录**，成功后清除标记并写一条服务日志 | 补做不是一次备份运行，生成一条 `running/success` 记录会污染运行记录与时间线，也会影响「最近一次运行」「上次成功」这些基于运行记录的判断。可观察的痕迹是标记消失与应用日志。否决：补做也生成运行记录（必须给运行增加新的触发方式，且会改变 `Attention`、`Stale`、时间线与列表里「上次运行」的含义） |
| 9 | 补做失败（非撞锁）时保留标记与原因，**下一轮继续重试**，但同一原因只记一次日志 | 标记的意义就是「还欠一次」；失败原因通常需要人处理（例如密钥被换掉），重试本身不造成副作用。同一原因不重复刷日志，避免每 30 秒一条 |
| 10 | 撞锁延后**不发送任何通知** | 通知事件是失败、恢复正常、太久没有成功、每次成功（`docs/specs/2026-10-15-opsnap-v1.md` 通知一节）。延后不属于其中任何一种，新增事件类型会扩大通知协议的维护面。否决：新增「清理延后」事件 |
| 11 | forget 的重试上限是 5 分钟，并且不超过本次运行的剩余超时与停止信号 | 固定 5 分钟不设为面板选项：多一个设置只增加决策负担，而 5 分钟覆盖了绝大多数备份间隙。运行被停止或超时（ctx 结束）时重试立即返回，与「超时/停止 ⇒ 本次运行失败、不留快照」的既有行为一致 |
| 12 | 运行详情里 forget 步骤显示「已跳过」与一句人话原因，不再显示 restic 的原始 JSON | 原始 JSON 里的 `unlock` 提示会诱导人去做有害操作（问题 4）。原始输出仍在运行日志里，排查时能看到 |
| 13 | 步骤状态「已跳过」在界面上统一用中性灰的完成态显示，不再显示序号 | 现在 `skipped` 在前端落到「未开始」的样式，与「这条已经处理过、只是没做事」不符；同一个状态有两种外观反而更难理解 |

## 清理旧快照的三种结局

一次运行的「清理旧快照」步骤有且只有这三种结局：

1. **正常删除**：restic 在重试窗口内拿到独占锁，按保留规则删除过期快照。步骤「成功」，日志写出删除了几个快照。
2. **延后补做**（新增）：重试窗口内一直撞锁。
   - 运行状态记为**成功**（快照已完整生成）。
   - forget 步骤记为「已跳过」，提示「存储位置正被其他备份占用，稍后自动补做」，日志记一条同样的说明（不带 restic 原始 JSON）。
   - 该任务被打上「待清理」，锚点是首次延后的时间；已有锚点时保留原时间，不覆盖。
3. **失败**：forget 因被锁以外的原因失败（含运行被停止或超时）。行为与现在一致——运行记为「有警告」，原因写明，进「需要处理」。

运行被停止或超时发生在 forget 期间时不算延后：按既有行为整次运行失败、回滚本次快照。

## 空闲时补做

**前置条件：** 至少有一个任务带「待清理」，且它所属的存储位置在本进程内没有备份在写也没有维护在进行。

**动作：** 调度器按存储位置逐个处理它的待清理任务，每个任务用**该任务当前的保留规则**执行一次 forget，且只删除带该任务标签的快照（与正常运行时的限定一致）。

**结果：**

- 成功：清除该任务的「待清理」与失败原因，写一条服务日志（任务名、删除了几个过期快照）。
- 撞锁（存储位置在这之后又被占用）：保留标记，等下一轮。
- 其他失败：保留标记并把原因换成本次的，等下一轮；与该任务上一次记录的失败原因相同时不再写日志。
- 存储位置不存在或读取任务失败：记一条服务日志，不影响其他存储位置与其他任务。
- 补做期间该存储位置上的备份与维护（例如管理员点了「校验数据」）都不会与它同时进行；补做不做 preflight，也不会因为本地目录被卸载而写入任何数据——这类失败会以 restic 错误的形式落到「其他失败」。
- 接口与面板：带「待清理」的任务在任务列表里显示一个小标记「待清理」，展开写明首次延后时间与最近的失败原因（如果有）；该标记不影响任务的 `attention`，也不影响「需要处理」筛选与概览的计数。

## 与其他既有行为的关系

- `docs/specs/2026-10-15-opsnap-v1.md` 的「一次运行」第 3 步与「有警告」的定义（目前只由 rsync 退出码 24 触发）保持其余部分不变；本文把「清理旧快照因仓库被锁而没做」从「有警告」移到「成功 + 待清理」。
- 「失败或不完整的导出不能记为成功的快照」不受影响：待清理只涉及删除过期快照，本次运行的快照 ID 与数据量照旧记录。
- 面板上的「解除仓库锁」保持需要二次确认、且只在确认没有备份或维护时使用；本文不改动它，也不因为它做任何自动操作。
- 运行记录保留期限与日志内容不变；待清理信息不随运行记录过期而消失（它在任务上，直到补做成功）。

## Out of scope

- 跨进程（多个 opsnap 实例指向同一存储位置）的协调，以及为此引入的外部锁服务。
- 把 forget 与 prune 合并、或改变「空间回收交给每周维护」的既有分工。
- 为「待清理」新增通知事件、概览区块或存储位置页面上的计数。
- 面板上把 `--retry-lock` 时长做成可配置项。
