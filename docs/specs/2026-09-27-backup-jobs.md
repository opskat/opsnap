# 备份任务：新建向导、MySQL / PostgreSQL 全量、调度与保留

> Status: Draft
> Owner: OpsNap 产品负责人
> Last updated: 2026-09-28

**Objective:** 管理员能通过五步向导，为 MySQL 或 PostgreSQL 数据源创建备份任务。任务按计划用官方工具做全量导出，把结果加密存进所选存储的 kopia 仓库，按保留策略清理旧快照。每次运行都留下运行记录。

**Hard invariant:**

1. **被标记为“成功”的运行，必须有一份可恢复的快照。**
   - 导出工具正常退出、导出内容通过完整性检查、kopia 快照写入并读回校验，三者都确认后才标记成功。
   - 失败、取消、超时的运行不形成快照。
2. **秘密不出现在导出工具的命令行参数、服务日志、运行日志和任何接口响应中。**
   - 秘密包括：数据库密码、TLS 客户端私钥、SSH 凭据、仓库密钥、S3 凭据。
   - 交给导出工具的凭据只写进权限为 0600 的临时文件。运行结束后，无论成功、失败还是取消，都要删除这些文件。OpsNap 启动时清理上次异常退出遗留的临时文件。
3. **保留策略和“同时删除快照”只删除本任务产生的快照。**
   - 不删除其他任务的快照，也不删除仓库中不是 OpsNap 产生的快照。
   - 本任务最新的一份成功快照，永远不会因为保留策略被删除。
4. **备份不修改数据源上的数据或配置。**

标记说明：〔已核实〕= 查证过源码或官方资料；〔用户决定〕= 本轮讨论中用户已确认；〔默认〕= 按常规做法先定、用户已认可设计。

## 问题

1. **还没有备份任务。** 侧栏「任务」是占位页〔已核实，main 915dd66，`frontend/src/App.tsx` 对 `/jobs` 渲染 `ComingSoonPage`〕。数据源和存储都已就绪，但不能真正备份。
2. **kopia 仓库只能创建和解锁，不能写入。** 仓库层只有建库、校验密钥、统计快照数〔已核实，`internal/pkg/kopiarepo/repo.go`〕。没有写快照、压缩、保留和用量统计。
3. **外部导出工具只认主机和端口。** 数据源可能要经过 SSH 跳板或 SOCKS5 代理才能连通，但 `mysqldump` / `pg_dump` 不理解这些链路。现有连接层只给 Go 驱动提供连接〔已核实，`internal/pkg/dsconn`、`internal/pkg/netchain`〕。
4. **没有调度器。** 服务里没有定时执行任何任务的机制〔已核实〕。

## 角色与用户故事

1. 作为**管理员**，我想用向导为一个 MySQL 实例的几个库建立每天凌晨的全量备份，存到 S3，保留最近 7 天全部、每周 4 份、每月 6 份。
2. 作为**管理员**，我想在任务列表一眼看到哪些任务最近失败、正在运行或在排队，并能立即重跑。
3. 作为**管理员**，我想点开一次失败的运行，看到失败在哪一步、原因是什么、执行日志是什么。
4. 作为**管理员**，我想在 OpsNap 停机维护后，错过的备份能自动补上一次。

| 2 | 本轮做不了的选项显示但禁用，标“后续版本支持”；第 4 步不显示通知区块〔用户决定〕 | 涉及：任务类型“同步”、服务器文件数据源、“全量 + 增量”。用户能提前知道这些会有；通知渠道在第 7 轮，没有渠道时勾选了也发不出去。否决：全部隐藏；显示通知并保存设置 |

| 4 | OpsNap 停机期间错过的计划，启动后每个任务补跑一次；同一任务上一次还没结束时，这次跳过并记录〔用户决定〕 | 否决：不补跑、只记“错过”；重叠时排队 |
| 5 | 删除任务时默认保留它的快照，确认框里可以勾选“同时删除该任务的 N 份快照”，默认不勾〔用户决定〕 | 误删任务不会丢数据；不勾时，快照仍可用 kopia 命令行恢复，第 7 轮的快照页也能看到。同时修订存储 spec 的不变式 1：OpsNap 只会删除它自己的任务产生的快照（保留策略或用户明确勾选），其他数据仍不删除、不覆盖。否决：始终保留（本轮无法释放空间）；一并删除（误操作不可恢复） |
| 6 | 任务列表、任务详情、向导第 2 步 PG 版的布局按新画的三张设计稿〔用户决定〕 | 沿用「数据源」页的样式 |
| 7 | 不提供设计稿中的“额外 mysqldump 参数”；高级选项只有“排除表”〔默认〕 | 任意参数（例如 `--result-file`）能让导出工具在主控端写任意文件，也能绕过“秘密不进命令行”。否决：开放参数加黑名单（难以列全） |
| 8 | 仓库中不存在设计稿里那种 `…/2026-09-23T02-00.zst` 物理文件；第 3 步显示“仓库内位置：`<存储名>:/<路径前缀>`”〔默认〕 | kopia 按内容分块存储，快照是清单而不是单个文件〔已核实，kopia 仓库格式〕。否决：照设计稿显示一个并不存在的路径 |
| 9 | 第 4 步的“长期占用估算”改为“按当前计划，最多保留约 K 份快照”；第 5 步只估算源数据量，不估算耗时〔默认〕 | 首次运行之前，不知道导出体积、压缩率和吞吐，给出的 GB 数和分钟数都是猜的；份数和源数据量可以准确算出。否决：按经验系数估算体积和耗时 |
| 10 | 数据源、存储、路径前缀在任务创建后不能修改，需要时新建任务〔默认〕 | 这三项决定快照归属。改了会让保留策略和历史快照对不上。否决：允许修改（旧快照变成无主快照） |
| 11 | 全局最多同时运行 3 个备份，其余排队，显示“等待中”〔默认〕 | 补跑可能在启动时同时触发多个大备份，需要限流，保护主控端和数据源。否决：不限并发 |
| 12 | 每次重试单独一条运行记录，标“重试 i/N”〔默认〕 | 每次尝试的开始时间、耗时、日志都不同，分开记录最清楚。否决：多次尝试合并为一条 |
| 13 | 被任务引用的数据源、存储不能删除；被任务引用的存储不能更改位置〔默认〕 | 与网络通道的引用保护一致。更改位置会让任务写到另一个仓库，历史快照与保留策略就断了。修订存储 spec「删除存储」中“后续轮次禁止删除”的说明，使之生效 |
| 14 | 导出工具经本机 127.0.0.1 上的临时端口连接数据源，这个端口转发到网络通道链路；运行结束即关闭〔默认〕 | 复用已有的逐跳拨号与主机密钥校验，外部工具不需要理解 SSH / SOCKS5。否决：让用户保证主控端可以直连数据库 |
| 15 | MySQL 一次导出覆盖所有选中的库，写成一个文件；PG 每个库单独导出一份 custom 格式归档〔默认〕 | MySQL 一次导出时，跨库是同一个事务快照，所以一致〔已核实，`--single-transaction` 语义〕；`pg_dump` 一次只能导出一个库〔已核实〕，custom 格式可以按表恢复。否决：MySQL 每库一个文件（跨库不一致） |

## 任务与新建向导

**前提**：已登录（浏览器会话或 API 令牌），至少有一个 MySQL / PostgreSQL 数据源和一个状态为“正常”的存储。

「任务」页右上角的“新建任务”打开向导，地址为 `/jobs/new`。向导共五步：**类型与数据源 → 内容与方式 → 目的地 → 计划与保留 → 确认**。

- 顶部步骤条显示当前步骤。已完成的步骤可以点击返回修改，返回时已填的内容不丢失。
- 当前步骤有不合法的输入时不能进入下一步，错误显示在对应字段旁。
- 取消时，如果已经填写过内容，需要二次确认；确认后放弃，不保存任何内容。

### 第 1 步：类型与数据源

- 任务类型为“备份”（默认选中）或“同步”。“同步”禁用，标“后续版本支持”。
- 数据源列表显示每个数据源的名称、类型、地址、连接状态和探测摘要，格式与数据源列表一致。
  - 服务器文件数据源禁用，标“后续版本支持”。
  - 状态不是“正常”的数据源可以选中，但行内提示原因（例如“主机密钥已变化”），而且这一步不能进入下一步，直到状态恢复。
- 选中后，该行显示探测摘要，例如“6 项通过 · 1 项提醒”。
- 没有可用数据源时显示空状态，引导到「数据源」页新建。

### 第 2 步：内容与方式

- **探测面板**：显示所选数据源的探测结果与探测时间，可以“重新探测”。“有风险”和“不可用”的项附修复方法，与数据源详情页一致。
  - 如果探测判定主控端导出工具不可用（`mysqldump` 找不到；`pg_dump` 找不到或大版本低于服务端），“仅全量”也不可选，并显示原因和修复方法，不能进入下一步。
- **备份范围**：“整个实例”或“指定数据库”。
  - 数据库列表在进入这一步时从数据源实时读取，显示库名和数据量。读取失败时显示原因与重试。
  - “指定数据库”至少选一个库。
  - MySQL 的“整个实例”不包含 `information_schema`、`performance_schema`、`sys`、`mysql`。PostgreSQL 的“整个实例”指所有允许连接的非模板库。
  - “整个实例”在每次运行时重新列出库，新建的库会被自动包含。“指定数据库”中的库在运行时不存在，本次运行失败，并指出是哪个库。
- **备份方式**：“仅全量”（选中）。“全量 + 增量（binlog）”（MySQL）和“物理全量 + WAL 增量”（PostgreSQL）禁用，标“后续版本支持”。
- **MySQL 选项**：
  - 说明全量工具为 `mysqldump`（官方），用一致性快照导出，不锁 InnoDB 表。
  - 一并备份：存储过程与函数、触发器、事件（默认都勾选），账号与权限（默认不勾）。
  - 账号与权限只导出非系统账号的 `CREATE USER` 与 `GRANT` 语句。数据源账号没有读取权限时，本次运行失败，并说明需要的权限。
- **PostgreSQL 选项**：
  - 说明全量工具为 `pg_dump`（官方），每个库一份 custom 格式归档。
  - 一并备份：“角色、表空间等全局对象”（默认勾选）。数据源账号没有读取权限时，本次运行失败，并说明需要的权限。
- **高级选项**（默认折叠）：只有“排除表”。
  - MySQL 写作 `库.表`，PostgreSQL 写作 `库.模式.表`，每行一个。
  - 格式不对时在字段旁提示。所指的表不存在时不报错，运行日志里提示“排除规则未匹配任何表”。

### 第 3 步：目的地

- 选择存储。列表显示存储名称、类型、位置和状态。状态不是“正常”的存储不可选，并显示原因。
  - 没有存储时显示空状态，引导到「存储」页新建。
- **路径前缀**：
  - 默认为 `<数据源类型>/<数据源名称>`，其中的非法字符替换为 `-`。
  - 只允许字母、数字和 `._-/`，1–128 个字符，不能以 `/` 开头或结尾，不能含 `..` 或连续的 `/`。
  - 同一存储中，不能和其他任务的前缀相同，也不能一个是另一个的上级。冲突时提示与哪个任务冲突。
  - 下方实时显示“仓库内位置：`<存储名>:/<路径前缀>`”。
- **压缩**：不压缩 / gzip / zstd，默认 zstd。
- **加密**：只读显示“已加密”和仓库密钥指纹，说明加密是存储的属性，不能在这里修改。

### 第 4 步：计划与保留

- **频率**：
  - 每小时：选择在第几分钟执行；
  - 每天：选择执行时刻；
  - 每周：选择一到多个星期几，以及执行时刻；
  - 自定义 Cron：标准 5 段表达式（分 时 日 月 周）。表达式不合法时，在字段旁提示原因。
- **时区**：默认使用浏览器的时区，可以从 IANA 时区列表中选择。
- 下方显示“接下来三次：…”，由服务端按所选时区计算，与实际调度一致。
- **保留策略**：
  - 保留最近 N 天内的全部快照，N 为 1–365，默认 7；
  - 更早的快照，每周保留最后一份，W 为 0–520 周，默认 4；
  - 每月保留最后一份，M 为 0–120 月，默认 6；
  - 下方显示“按当前计划，最多保留约 K 份快照”，以及“本任务最新的一份成功快照始终保留”。
- **失败处理**：
  - 失败重试 0–5 次，默认 2；重试间隔 1–120 分钟，默认 5；
  - 超时时长 10 分钟到 48 小时，默认 2 小时。
- 不显示“全量周期”（只有“全量 + 增量”才需要）和通知区块。

### 第 5 步：确认

- **任务名称**：默认“`<数据源名称>` 全量备份”，1–64 个字符，任务之间不能重名。
- 四组摘要（类型与数据源、内容与方式、目的地、计划与保留），各带一个“修改”入口，点击回到对应步骤。
- **创建后**：“立即执行一次”（默认），或“等下一次计划”（显示下次执行时间）。
- 底部显示“首次为全量备份，所选库的源数据量约 X”，并说明导出和压缩后通常更小。数据量读取失败时，这一行显示“无法估算”，不影响创建。
- 点击“创建任务”后创建并启用任务，进入该任务的详情页。创建失败时停留在第 5 步并显示原因。

### 编辑、暂停、删除

- **编辑**：沿用向导，预填现有设置。
  - 数据源、存储、路径前缀只读显示，并说明“创建后不能修改”。
  - 保存后，新的计划和保留立即生效；正在进行的运行按开始时的设置完成。
- **暂停 / 启用**：暂停后计划不再触发；已在运行或排队的运行不受影响。
  - 暂停期间可以“立即执行”。
  - 启用后从下一次计划时间开始，暂停期间的计划不算“错过”，不补跑。
- **删除**：二次确认。
  - 确认框显示任务名称，以及一个默认不勾的“同时删除该任务的 N 份快照”。
  - 任务正在运行或排队时不能删除，提示先取消。
  - 删除后，任务和它的运行记录一并删除。
  - 不勾选时，快照留在仓库中；勾选时，只删除带有本任务标签的快照。删除快照失败时，任务仍然删除，并提示有多少份快照未能删除，可以用 kopia 命令行手动处理。

## 执行

一次运行指按任务设置完成一次全量备份。触发方式有四种：计划、手动（“立即执行”）、补跑、重试。

**排队**：全局最多同时运行 3 个，其余按触发顺序排队，状态为“等待中”。同一任务同时最多只有一个运行或排队中的运行：

- 计划到点时，如果该任务已在运行或排队，本次记为“跳过”，原因为“上一次仍在运行”；
- 已在运行或排队时，“立即执行”按钮不可用。

**执行步骤**：运行日志按以下步骤记录，失败时指出失败在哪一步。

1. **准备**：检查存储状态为“正常”、数据源状态不是“主机密钥已变化”、导出工具可用。任何一项不满足就失败，不发起连接。
2. **连接数据源**：沿网络通道建立链路，主机密钥校验与数据源测试完全一致。在本机 127.0.0.1 开临时端口，把导出工具的连接转发到链路上。
3. **导出并写入仓库**：
   - 导出工具的输出直接流式写入一个新的 kopia 快照，主控端不落地完整的导出文件。
   - MySQL：一个 `.sql` 文件包含所有选中的库；勾选账号与权限时另有一个文件。
   - PostgreSQL：每个库一个 custom 格式归档；勾选全局对象时另有一个文件。
   - 导出进行中，运行记录显示已导出的字节数。
4. **校验**：
   - 导出工具以成功状态退出；
   - MySQL 导出以 `mysqldump` 的完成标记结尾，PostgreSQL 归档头完整；
   - kopia 快照清单写入成功，并能读回快照中每个文件的大小与内容标识。
5. **应用保留策略**：只在成功之后执行，见「保留」。删除失败只写进运行日志，本次运行仍为成功。

**导出一致性**：

- MySQL 使用单一事务快照：InnoDB 表之间一致；非 InnoDB 表不保证一致，运行日志会列出这些表。
- 导出文件不包含 GTID 清除语句，以便导入到另一台实例。
- PostgreSQL 每个库内部一致，库与库之间不保证一致。

**恢复要求**：成功快照中的导出文件，用 kopia 官方命令行取出后，可以用对应的官方客户端（`mysql`、`pg_restore`/`psql`）导入到一台空的、同大版本的实例，导入后数据与导出时一致。

**快照标签**：每份快照标注任务 ID、运行 ID、类型（全量）、数据源类型，用于保留、删除和以后的快照页。

**取消**：运行中或排队中的运行可以取消。取消后终止导出工具，关闭端口转发，删除临时文件，不形成快照，状态为“已取消”。

**超时**：运行时间超过任务设置的超时时长时，按取消的方式终止，但状态为“失败”，原因为“超时（超过 X）”。

**重试**：失败（包括超时）后，按任务设置等待间隔后重试，直到用完次数。

- 每次重试是一条新的运行记录，标“重试 i/N”。
- 取消和跳过不触发重试。
- 等待重试期间，如果下一次计划时间已到，未开始的重试作废，改为执行计划运行。

**导出工具**：先在 PATH 中查找，再在 `tools.dir` 中查找，与探测一致。`mysqldump` 版本低于服务端时照常执行，运行日志里提示；`pg_dump` 大版本低于服务端时失败，附修复方法。

**OpsNap 重启**：

- 重启时正在运行的运行记为“失败”，原因为“OpsNap 重启，运行中断”，不触发重试；
- 重启时仍在排队的运行记为“已取消”，原因为“OpsNap 重启”；
- 然后按「调度」补跑错过的计划。

## 调度

- 每个启用的任务按自己的频率和时区触发。夏令时切换时，按该时区的墙上时间执行：不存在的时刻顺延到切换后，重复的时刻只执行一次〔默认〕。
- **补跑**：启动后，对每个启用的任务检查“上一次计划时间”是否已经执行过（有运行记录，包括跳过）。没有的话，立即触发一次补跑；错过多次也只补一次。
- 暂停期间的计划不算错过。任务创建之前的时间也不算。

## 保留

每次成功运行后，只对本任务带标签的快照执行，时间按任务时区计算：

1. 最近 N 天内（从本次运行开始时间往前推 N×24 小时）的成功快照全部保留；
2. 更早的快照，按自然周（周一开始）分组，每组保留最后一份，保留最近 W 周；
3. 按自然月分组，每组保留最后一份，保留最近 M 个月；
4. 本任务最新的一份成功快照始终保留；
5. 其余快照删除。删除的空间要在 kopia 仓库维护后才释放：
   - 每次删除后做一次快速维护；
   - 每个被任务使用的存储每天做一次完整维护〔默认〕。

同一份快照同时满足多条规则时，只算保留一次。修改保留策略后，从下一次成功运行开始按新策略执行。

## 运行记录

- **状态**：等待中、运行中、成功、失败、已取消、跳过。
- **每条记录包含**：
  - 触发方式：计划、手动、补跑、重试 i/N；
  - 开始时间、结束时间、耗时；
  - 导出体积（导出工具输出的字节数）；
  - 新增上传量（去重、压缩后实际写入仓库的字节数）；
  - 快照 ID（仅成功）；
  - 失败在哪一步及原因（仅失败）。
- **执行日志**：
  - 每行带时间和步骤名；
  - 导出工具的错误输出去掉秘密后并入日志；
  - 每次运行最多保留 1000 行，超出时保留开头和结尾，中间注明省略了多少行〔默认〕。
- 每个任务最多保留最近 1000 条运行记录，更早的自动删除〔默认〕。

## 任务列表

地址为 `/jobs`，侧栏「任务」。

- **每行显示**：
  - 名称，以及类型、备份范围（“整个实例”或“N 个库”）、启用状态；
  - 数据源 → 存储，以及路径前缀；
  - 计划的描述（例如“每天 02:00”），以及下次执行时间；暂停时显示“已暂停”；
  - 最近一次运行：状态标签、时间与耗时或失败原因、运行中时的已导出量；
  - 当前快照数。
- **行操作**：
  - “立即执行”：已在运行或排队时不可用；
  - 运行中时，“立即执行”换成“取消运行”；
  - “编辑”；
  - 更多菜单：暂停 / 启用、查看详情、删除任务。
- 点击名称进入详情页。
- 列表中运行中、排队中的状态会自动刷新，无需手动刷新页面。
- 没有任务时显示空状态，引导“新建任务”。加载失败时显示错误与重试，不出现空白页。

## 任务详情

地址为 `/jobs/<id>`。

- **头部**：
  - 返回「任务」；
  - 名称和启用状态；
  - 数据源 → 存储、计划和下次执行时间；
  - 操作：暂停 / 启用、编辑、立即执行（运行中时为“取消运行”）。
- **配置**：
  - 数据源、备份范围、一并备份的对象、备份方式、存储、仓库内位置、压缩、加密与密钥指纹；
  - 计划和接下来三次、保留策略、失败处理。
- **统计**：
  - 快照数和最早快照时间；
  - 仓库占用：本任务现存快照引用的数据块，去重、压缩后在仓库中的大小，另显示导出总量与节省比例；
  - 最近一次成功的时间、耗时和新增上传量；
  - 最近 30 次运行的成功数、失败数和成功率。
- **运行记录**：
  - 按开始时间倒序，每页 20 条；
  - 列：状态、触发方式、开始时间、耗时、导出量 / 新增量、快照 ID；
  - 点击一行，在其下方展开：失败时的失败步骤与原因，以及执行日志。
- 运行中的记录自动刷新。
- 任务不存在时显示“任务不存在”，并提供返回列表的入口。

## 对已有页面的影响

- **数据源**：
  - 被任务引用时不能删除，删除菜单项不可用，并列出引用它的任务；
  - 数据源详情页显示“被 N 个任务使用”。
- **存储**：
  - 被任务引用时不能删除，也不能更改位置，对应入口不可用，并列出引用它的任务；
  - 存储列表显示“被 N 个任务使用”。

## 敏感数据

- 交给 `mysqldump` 的密码与 TLS 材料写进 0600 的选项文件；交给 `pg_dump` 的密码写进 0600 的密码文件，TLS 材料写进 0600 的文件。命令行参数中不出现任何秘密。
- 运行日志、服务日志和接口响应中不出现秘密。导出工具的错误输出如果包含秘密，先去掉再记录。
- 导出内容本身只以加密形式写入 kopia 仓库，主控端不落地完整的导出文件。

## 权限

- 浏览器会话与 API 令牌都可以管理任务，包括查看、新建、编辑、暂停、删除、立即执行、取消、查看运行记录与日志〔默认，与数据源一致〕。

  - 任务列表、任务详情；
  - 新建 / 编辑任务向导五步（第 2 步分 MySQL 与 PostgreSQL 两种）；
