# OpsNap v1: self-hosted server backup and sync

> Status: Draft
> Owner: OpsNap product owner
> Last updated: 2026-09-23

**Objective:** An operator deploys OpsNap on a server they own and, from a browser, backs up MySQL, PostgreSQL, MongoDB, Redis, Kafka and server files on a schedule to a local directory or S3-compatible storage, and restores data from those backups.

**Hard invariants:**

1. A snapshot marked "successful" must be restorable. If any step of the run is not confirmed complete, the snapshot must not be marked successful.
2. Storage credentials and repository keys are kept only on the OpsNap controller and are never sent to the servers being backed up.

Markers: [verified] = checked against source code or official material; [user-decided] = confirmed by the user during this round. The design file `/Users/codfrm/Code/设计稿/opsnap.pen` is reference only; this document is authoritative.

## Problem

1. **Backup tooling for self-managed servers is fragmented.** Databases, middleware and files each get their own scripts (crontab + mysqldump + rsync and so on). Failed runs, missed runs and unusable backup files are often discovered only at restore time. [user statement]
2. **Incremental capability varies by engine and deployment, and users cannot tell in advance whether it will work.** For example, MySQL binlog increments require binlog enabled, ROW format and replication privileges; a standalone MongoDB has no oplog; Redis has no incremental mode. [verified, see "Full and incremental backup per engine"]

## Actors and user stories

1. As an **operations engineer**, I want to see the latest run status of every backup and sync job on one page, so that I notice failed and missed jobs immediately.
2. As an **operations engineer**, I want to know while creating a job which backup methods a data source supports and which prerequisites are missing, so that I do not discover at restore time that increments were never being collected.
3. As an **operations engineer**, I want backups encrypted before they go to S3, and I want to recover data with my offline copy of the key even if OpsNap itself is lost.
4. As a **notification recipient**, I want to be notified when a job fails, misses its schedule, or storage is nearly full.

## Design decisions

| # | Decision | Basis and rejected options |
|---|---|---|
| 1 | Product name OpsNap, a standalone product [user-decided] | opsnap.dev / opsnap.io were available and the name was free on npm / PyPI / Homebrew. Rejected: opsbackup (too generic for a standalone product), OpsVault (clashes with an existing MySQL/PG backup project) |
| 2 | A self-hosted web console: one Go binary with the frontend embedded [user-decided] | Scheduled jobs need a long-running service. Rejected: desktop client (cannot run schedules while the machine is off), CLI plus a read-only web page |
| 3 | No resident agent in v1; the controller connects to everything remotely [user-decided] | Lower deployment and operating cost. Rejected: controller plus resident agents. Consequently there is no "Nodes" page |
| 4 | Server files use an "SSH ephemeral executor" [user-decided] | Each run pushes a worker over SSH and deletes it afterwards; nothing stays resident, so this does not conflict with decision 3. Rejected: SFTP-only reads (too slow for millions of files; kept as a fallback); rsync into a local mirror (the controller would need as much disk as the source). Directory sync uses the rsync delta algorithm through a pure-Go implementation embedded in the executor, without depending on an rsync binary on the servers |
| 5 | kopia is the storage layer, embedded as a Go library [user-decided] | kopia is Apache-2.0 and actively maintained [verified]. It provides chunked deduplication, encryption, snapshot manifests, retention and integrity checks, with native local and S3 backends. Its Repository Server mode lets an executor upload only missing chunks without holding storage credentials. Rejected: a home-grown dedup repository (large effort, high risk); WAL-G (its repository format would conflict with ours, and it is designed to run on the database host) |
| 6 | MySQL and PostgreSQL full backups use the official tools, with no user choice of tool [user-decided] | Official tools are the most stable and compatible. Rejected: third-party tools such as mydumper as an option; `xelabs/go-mydumper` is archived and GPL-3.0 [verified] |
| 7 | Increments use pure Go where possible: MySQL binlog through the replication package of `go-mysql-org/go-mysql`, PostgreSQL physical base backup plus WAL through `jackc/pglogrepl` [library capabilities verified; adoption user-decided] | The controller does not need `mysqlbinlog` or `pg_receivewal` installed. Note: the dump package of `go-mysql` still shells out to `mysqldump` [verified] |
| 8 | Keep the "full + incremental" model and enable it per data source based on probing [user-decided] | Engine capabilities differ widely. Rejected: one global switch; rejected: "full backups plus dedup only, no increments" |
| 9 | Backup and sync share one "Jobs" entry, distinguished by type [user-decided] | Their configuration flows are almost identical. Rejected: two separate menus |
| 10 | Encryption keys belong to a storage target, are held by the server, are system-generated by default, and may be user-chosen [user-decided] | Scheduled jobs must run unattended. Rejected: server does not hold the key (schedules could not run); one key per job (too many keys to match up during disaster recovery) |
| 11 | Storage supports only a local directory and S3-compatible services [user-decided] | The S3 protocol covers AWS, Aliyun OSS, Tencent COS, MinIO, R2 and others. Rejected: SFTP as storage |
| 12 | Visual style is the dark "Terminal" look, with dark and light themes, UI in Chinese and English [user-decided] | Design file: `/Users/codfrm/Code/设计稿/opsnap.pen`. Rejected: the "Clean" light and "Snap" warm directions |

## Deployment and runtime

- Runs as one Go binary with the web frontend embedded; a Docker image is also provided.
- **The Docker image bundles several versions of `mysqldump` and the PostgreSQL client tools**; the program picks the version matching the server. With the standalone binary, probing checks that local tools exist and match the server version. [user-decided: both distributions]
- The program's own data (configuration, jobs, run history, held keys) is stored locally on the controller. Held repository keys and data source credentials are stored encrypted and never written to disk in plain text.
- **Login**: on first start the user is guided to create the single admin account. Without a session, no page or API is accessible.
- **API tokens**: the admin can create tokens, see when each was last used, and revoke them. A token is shown in full only once, at creation; revocation takes effect immediately.

## Information architecture

The sidebar lists **Overview, Jobs, Snapshots & Restore, Sources, Storage**, then **Notifications** and **Settings** under a "System" group.

- Page titles, buttons and status labels switch between Chinese and English. Numbers, addresses and durations use a monospaced font.
- All colours come from design variables; text contrast meets WCAG AA in both themes (normal text ≥ 4.5:1, icons ≥ 3:1).
- Wherever text sits on a green fill (buttons, solid badges), use the darker `primary` green with white text; the brand mint is reserved for decorative emphasis such as highlighted numbers, charts and the logo.

## Overview

- Four stats: number of protected data sources, 24-hour success rate, storage used (after dedup, with the saved percentage), and the next run time with its job.
- A recent-runs list filterable by "All / Backup / Sync / Failed", with statuses succeeded, running (with progress), failed, queued, and live sync.
- A 14-day run bar chart (successes and failures counted separately) and usage per storage target.
- An empty state guides the user to add data sources and storage; a failed load shows an error state, never a blank page. (Not yet in the design file.)

## Data sources and capability probing

A data source is a reusable connection profile: address, port, credentials, TLS and, when needed, an SSH jump host. For the server-files type it is an SSH-reachable host plus directories. Sync targets are also chosen from data sources.

**When probing runs**: automatically when a data source is saved, and on demand from the data source detail page and from step 2 of the job wizard. Results carry a timestamp and are cached.

**Probe results have three levels**: available, available with risk, unavailable. "Available with risk" and "unavailable" always state the reason. Every fixable item offers a copy-ready fix (SQL, a configuration item or a command).

**Probes per type**:

| Type | Probes |
|---|---|
| MySQL | version; whether `log_bin` is on; whether `binlog_format` is ROW; whether GTID is on; binlog retention; whether the account has REPLICATION SLAVE / CLIENT; whether non-InnoDB tables exist (if so, warn that a full backup needs a table lock); whether the controller's `mysqldump` matches the server version |
| PostgreSQL | version; `wal_level`; `max_wal_senders`; whether replication slots are available; whether the account has the REPLICATION attribute; whether the controller's `pg_dump` major version is at least the server's |
| MongoDB | replica set or standalone; oplog size and the resulting estimate of how long an interruption increments can tolerate; whether the account has the backup role |
| Redis | whether PSYNC is allowed; whether cluster mode is on; memory usage |
| Kafka | protocol version; ACLs for topics and consumer groups |
| Server files | SSH reachable; CPU architecture (amd64 / arm64); whether the temp directory allows executing programs; whether passwordless sudo is available; the filesystem of each target path, whether it is on an LVM volume, and free space in the volume group; estimated file count and total size |

**Failure handling**: if a probe cannot connect or times out, the result shows "could not probe" with the error; a previous cached result must never be presented as this run's success.

## Jobs and the job wizard

Jobs are either **backup** or **sync**.

The wizard has five steps: **Type & source → Content & method → Destination → Schedule & retention → Confirm**. Only step 2 changes with the data source type; the other four are the same for every type. Completed steps can be revisited by clicking them.

1. **Type & source**: choose backup or sync, then pick a data source from a list showing each source's connection status. The selected row shows a probe summary such as "6 passed · 1 warning". (Not yet in the design file.)
2. **Content & method**:
   - the probe panel at the top;
   - then backup scope, backup method, and a "<type> options" section, with rarely used options collapsed under "Advanced";
   - methods the probe marks unavailable are disabled with the reason; methods that do not exist for the type (such as Redis increments) are not shown at all.
3. **Destination**: choose the storage target (local directory or S3), set the path prefix (the resulting full path is shown live below it), and choose compression (none / gzip / zstd, default zstd). Encryption is a property of the storage target; this step only shows its encryption status and cannot change it.
4. **Schedule & retention**:
   - frequency: hourly / daily / weekly / custom cron, with the time zone and the next three run times;
   - full-backup cycle: shown only when step 2 chose "full + incremental";
   - retention by days, weeks and months, with a long-term storage estimate;
   - retry count and interval on failure, and a timeout;
   - notification triggers: "on failure" and "missed schedule" on by default, "on success" off by default.
5. **Confirm**: the job name is editable; each of the four summary groups has an "Edit" link; after creation the user chooses to run once immediately (default) or wait for the next scheduled run; the footer estimates the size and duration of the first full backup.

**Invalid input blocks the next step**, with the error shown next to the field — for example an invalid cron expression, an illegal path prefix, or a retention count of 0.

## Full and incremental backup per engine

| Type | Full | Incremental | Restore granularity |
|---|---|---|---|
| MySQL | official `mysqldump` with `--single-transaction`, recording the binlog position or GTID | pure-Go continuous binlog streaming [verified feasible] | any point in time with increments enabled, otherwise a snapshot |
| PostgreSQL, logical mode | official `pg_dump`, selectable per database | not supported | a snapshot |
| PostgreSQL, physical mode | pure-Go physical base backup (whole cluster) [verified feasible] | pure-Go continuous WAL streaming [verified feasible] | any point in time; restore requires the same PostgreSQL major version |
| MongoDB | `mongodump` from the official mongo-tools, embedded as a Go library (Apache-2.0 [verified]), nothing to install [user-decided] | oplog reading, replica sets only | any point in time for replica sets; a snapshot for standalone servers |
| Redis | RDB fetched over the replication protocol | not supported (no incremental option in the UI) | a snapshot |
| Kafka | no concept of a full backup | continuous resume by offset | replay to the target |
| Server files | first run is full | changes detected against the previous snapshot's file metadata; only missing chunks are uploaded | a snapshot, including single files or directories |

**Linking full and incremental backups**: a full snapshot records its log starting point (binlog position or GTID, WAL LSN, oplog timestamp), and increments continue from there. If the log has a gap (for example the source already purged its binlog), the job is marked "incremental interrupted", a notification is sent, and the next run automatically becomes a full backup. **Success must never be reported across a gap.**

## Sync jobs

Sync is **one-way**: data is copied continuously or periodically from the source to the target. The target is chosen from data sources and must be the same type as the source. Sync does not go through a repository and keeps no history.

Sync method per type [user-decided]:

| Type | Initialization | Ongoing sync | Trigger |
|---|---|---|---|
| MySQL → MySQL | export with official `mysqldump`, import into the target | pure-Go binlog streaming replayed on the target | continuous |
| PostgreSQL → PostgreSQL | export with official `pg_dump`, import into the target | logical replication (pgoutput) decoded and replayed | continuous |
| MongoDB → MongoDB | export with `mongodump`, import into the target | continuous oplog reading and replay (source must be a replica set) | continuous |
| Redis → Redis | fetch the RDB and load it into the target | receive the command stream as a replica and replay it | continuous |
| Kafka → Kafka | start consuming from a chosen position (earliest / latest / a timestamp) | continuous consumption written to the target topic, optionally syncing consumer group offsets | continuous |
| Directory → directory | push an ephemeral executor to both source and target and run an initial full sync with the rsync delta algorithm | repeat delta syncs on schedule | scheduled |

**Directory sync implementation**: no rsync binary is required on the servers. The rsync protocol comes from a pure-Go implementation (`gokrazy/rsync`, BSD-3-Clause [verified]) compiled into the ephemeral executor, so nothing is installed on either server.

**The directory sync transfer path is chosen per job** [user-decided]:
- **Direct**: the source executor connects to the target directly, which requires the source to reach the target. The controller issues one-time credentials for the run, invalidated when it ends.
- **Relayed through the controller**: the servers need not reach each other, but traffic passes through the controller.
- When "direct" is chosen, probing checks that the source can reach the target; if not, the job cannot be saved and the user is told to use the relay.

**Requirements**:

- **Visible lag**: continuous sync jobs show the current lag, such as "lag 1.2s", on the overview and the job detail page; exceeding a threshold triggers a notification.
- **Resume**: after the sync process restarts it continues from the last position confirmed written to the target, with no duplicate replay and no skipped data.
- **Interruption**: if the source's logs were purged and resuming is impossible, the job is marked "sync interrupted" and a notification is sent; the user decides whether to re-initialize. The target is never cleared automatically.
- **Target protection**: before initialization, a non-empty target triggers an explicit warning and a second confirmation.
- **Conflicts**: if replay fails because another program wrote to the target, the job pauses and shows the failing change. v1 has no automatic conflict resolution.

## Server files and the ephemeral executor

**Read modes**:
- **Direct read**: stream while reading; suits files that rarely change.
- **Filesystem snapshot**: LVM only for now. The executor creates a read-only snapshot, reads from it, and deletes it afterwards. Only paths on LVM volumes use snapshots; other paths are read directly, and the UI marks the mode per path.

**Run flow**:
1. The controller pushes the worker binary matching the server's architecture to a temp directory over SSH and runs it.
2. The worker connects as a client to the kopia repository server embedded in the controller, through an SSH tunnel.
3. The worker scans and chunks locally and uploads only chunks missing from the repository.
4. Afterwards the worker binary is deleted, along with any LVM snapshot it created.

**Credentials**: the worker never holds storage credentials or repository keys.

**Fallback**: if the temp directory does not allow executing programs, or the CPU architecture is unsupported, the run falls back to SFTP-only reads, and the job detail notes "fallback used, slower".

**Failure handling**: if the worker exits abnormally, SSH disconnects, or snapshot creation fails, the run is marked failed and the chunks already uploaded do not form a snapshot. The worker binary and LVM snapshot are cleaned up on a best-effort basis; anything left behind is listed with its path in the run record.

**Options**: exclude rules; whether to preserve permissions and ownership, extended attributes, and hard links; whether to follow symlinks. Advanced options: pre/post scripts, snapshot space limit, transfer rate limit, maximum single-file size.

## Storage, repositories and encryption

- Each storage target is one kopia repository backed by a local directory or S3-compatible storage. Jobs are separated by path prefix inside the repository, and snapshots are tagged with job ID, full or incremental, and log position.
- **Enabling encryption the first time**: adding a storage target opens "Set encryption key". By default the system generates a random key, with copy, download-key-file and regenerate actions and the key fingerprint shown; the user may switch to a self-chosen password. Encryption is enabled only after the user ticks "I have saved this key and understand data cannot be recovered without it".
- **Held key**: the key is stored encrypted on the controller for scheduled runs and restores. The UI states plainly that after the server is lost or reinstalled, only the user's offline copy can decrypt the backups.
- **Existing repository**: if a kopia repository already exists at the target location, "Unlock existing repository" opens, showing the repository's creation time and snapshot count and asking the user to paste the key or upload the key file. A wrong key shows "incorrect key" and the number of consecutive failures; overwriting or deleting the existing repository is not allowed.
- **No lock-in**: users can open an OpsNap repository with the official kopia CLI and their own key to restore data. Product documentation must say so.

## Snapshots and restore

- The snapshots page lists each job's snapshots, filterable by job, data source and time.
- Two ways to restore:
  - **From a snapshot**: every type.
  - **To a point in time**: only data sources with log-based increments (MySQL binlog, PG physical mode, MongoDB replica sets); the UI shows the restorable time range.
- Three restore targets:
  - **the original data source**;
  - **another data source of the same type**;
  - **export as a download**: the official tool's dump format for databases, an archive of the selected files or directories for server files.
- **Restoring to the original data source** is destructive: it requires a second confirmation in which the user types the data source name. By default a full snapshot of the original is taken first; the user may untick this.
- **PostgreSQL physical mode** restores write the target host's data directory, so the target must be an SSH-accessible host and the PostgreSQL instance must be stopped during the restore. The UI explains this when the target is chosen and refuses to start otherwise.
- Restores show progress and write the result to the run history; on failure they state which step failed and what state the target is in (for example "cleared, not yet written").
- Server files can restore a single file or directory, to the original path or another path; when a target file exists, the user chooses overwrite, skip or rename.

## Notifications

- Channels: email, webhook, Feishu, DingTalk, WeCom, Telegram [user-decided]. Slack is out of scope for v1.
- Every channel offers "send test message" and shows the delivery result in the UI.
- Triggers: job failed; missed schedule (the scheduled time passed without a run); abnormal duration or size; sync lag above threshold; storage nearly full; incremental interrupted.
- Every notification sent is recorded as an event, and events can be marked as handled.

## Out of scope

- Resident agents and the "Nodes" page
- Cloud disk snapshots (depend on provider APIs and restore only whole disks)
- Physical backups that must run on the database host, such as MySQL XtraBackup or copying Redis BGSAVE files; a later version may do these through the ephemeral executor
- Native ZFS / btrfs block-level increments: kopia's chunked dedup already covers most of the benefit
- Letting users choose the backup tool, e.g. mydumper
- SFTP as a storage backend
