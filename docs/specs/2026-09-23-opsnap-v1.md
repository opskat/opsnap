# OpsNap v1：自托管服务器备份与同步

> Status: Draft
> Owner: OpsNap 产品负责人
> Last updated: 2026-09-23

**Objective:** 运维人员在一台自己的服务器上部署 OpsNap，就能通过浏览器，把 MySQL、PostgreSQL、MongoDB、Redis、Kafka 和服务器文件，按计划备份到本地目录或 S3 兼容存储，并能从这些备份恢复数据。

**Hard invariant:**

1. 被标记为“成功”的快照必须能被恢复。流程中任何一步没有确认完成，快照都不能被标记为成功。
2. 存储凭据和仓库密钥只保存在 OpsNap 主控端，不下发到被备份的服务器。

标记说明：〔已核实〕= 查证过源码或官方资料；〔用户决定〕= 本轮讨论中用户已确认。设计稿见 `/Users/codfrm/Code/设计稿/opsnap.pen`，仅作参考，以本文为准。

## 问题

1. **自建服务器的备份工具零散。** 数据库、中间件、文件各用一套脚本（crontab + mysqldump + rsync 等）。执行失败、没按时执行、备份文件不可用，往往要到恢复时才被发现。〔用户陈述〕
2. **增量能力随引擎和部署方式变化，用户很难提前判断能不能用。** 例如 MySQL 的 binlog 增量要求开启 binlog、格式为 ROW、账号有复制权限；MongoDB 单机部署没有 oplog；Redis 不支持增量。〔已核实，见“各引擎的全量与增量”〕

## 角色与用户故事

1. 作为**运维工程师**，我想在一个页面上看到所有备份和同步任务最近的运行状态，这样能立即发现失败和没按时执行的任务。
2. 作为**运维工程师**，我想在新建任务时就知道这个数据源支持哪些备份方式、缺什么条件，这样不会等到恢复时才发现增量根本没在收。
3. 作为**运维工程师**，我想把备份加密后存到 S3，而且就算 OpsNap 本身坏了，也能用离线保存的密钥找回数据。
4. 作为**通知接收人**，我想在任务失败、超时未运行、存储快满时收到通知。

## 设计决策

| # | 决策 | 依据与被否决的方案 |
|---|---|---|
| 1 | 产品名 OpsNap，独立产品〔用户决定〕 | 确认 opsnap.dev / opsnap.io 可注册，npm / PyPI / Homebrew 同名未被占用。否决：opsbackup（名字太泛，不像独立产品）、OpsVault（已有同类 MySQL/PG 备份项目重名） |
| 2 | 形态为自托管 Web 控制台：Go 单二进制内嵌前端〔用户决定〕 | 定时任务需要长期运行的服务。否决：桌面客户端（关机后无法定时）、CLI 加只读 Web 页 |
| 3 | v1 不做常驻 Agent，主控端远程连接一切〔用户决定〕 | 降低部署和运维成本。否决：主控加常驻 Agent。因此导航中没有“节点”页 |
| 4 | 服务器文件使用“SSH 临时执行器”〔用户决定〕 | 每次任务时通过 SSH 推送 worker、执行完就删除，不常驻，与决策 3 不冲突。否决：纯 SFTP 读取（百万级文件太慢，只作兜底）；rsync 加本地镜像（主控端要占用和源目录一样大的空间）。目录同步任务使用 rsync 的差异算法，但由执行器内嵌的纯 Go 实现完成，不依赖服务器上的 rsync 程序 |
| 5 | 存储层引入 kopia（作为 Go 库嵌入）〔用户决定〕 | kopia 使用 Apache-2.0 许可，至今活跃维护〔已核实〕，提供分块去重、加密、快照清单、保留策略、完整性校验，原生支持本地和 S3。它的 Repository Server 模式能让执行器只上传缺失的数据块，而不持有存储凭据。否决：自研去重仓库（工作量大、风险高）、WAL-G（仓库格式会与我们冲突，而且设计上要跑在数据库主机上） |
| 6 | MySQL、PG 的全量使用官方工具，不给用户选工具〔用户决定〕 | 官方工具最稳、兼容性最好。否决：mydumper 等第三方工具作为可选项；`xelabs/go-mydumper` 已归档且为 GPL-3.0〔已核实〕 |
| 7 | 增量尽量用纯 Go：MySQL binlog 用 `go-mysql-org/go-mysql` 的复制模块，PG 的物理全量加 WAL 用 `jackc/pglogrepl`〔已核实库的能力，采用与否由用户决定〕 | 主控端不需要额外安装 `mysqlbinlog` 或 `pg_receivewal`。注意：`go-mysql` 的 dump 模块内部仍然调用 `mysqldump`〔已核实〕 |
| 8 | 保留“全量 + 增量”模式，并按探测结果逐个数据源开放〔用户决定〕 | 各引擎能力差异很大。否决：全局统一开关；否决“只做全量加去重，不做增量” |
| 9 | 备份和同步合并为一个“任务”入口，用类型区分〔用户决定〕 | 两者配置流程几乎一样。否决：拆成两个菜单 |
| 10 | 加密密钥绑定在存储上，服务端托管，默认由系统生成，也允许用户自设〔用户决定〕 | 定时任务要能无人值守地运行。否决：服务端不托管（定时任务无法自动运行）；按任务单独设密钥（密钥数量太多，灾难恢复时对应不上） |
| 11 | 存储只支持本地目录和 S3 兼容存储〔用户决定〕 | S3 协议已覆盖 AWS、阿里云 OSS、腾讯云 COS、MinIO、R2 等。否决：SFTP 作为存储 |
| 12 | 视觉风格为 Terminal 暗色系，同时提供深色和浅色主题，界面支持中文和英文〔用户决定〕 | 设计稿见 `/Users/codfrm/Code/设计稿/opsnap.pen`。否决：Clean 亮色、Snap 暖色两个方向 |
| 13 | v1 六种类型全部完成后再发布：MySQL、PostgreSQL、MongoDB、Redis、Kafka、服务器文件〔用户决定〕 | 功能完整再发布。否决：先发布 MySQL、PG、文件三种 |
| 14 | v1 包含同步任务〔用户决定〕 | 否决：v1 只做备份 |
| 15 | 单管理员账号，可选绑定一个 OIDC 身份；加可生成的 API 令牌〔用户决定，2026-09-23 修订：增加 OIDC〕 | 满足个人和小团队使用，并能接入已有的统一登录。否决：多用户、角色、审计日志，这些放到后续版本；按白名单允许多个 OIDC 账号登录（等于多用户）。细节见 [管理员认证 spec](2026-09-23-admin-auth.md) |
| 16 | 同时提供 Docker 镜像和单二进制〔用户决定〕 | 镜像预装官方工具，开箱即用；单二进制由探测提示缺什么。否决：只提供镜像 |

## 部署与运行

- 以单个 Go 二进制文件运行，内嵌 Web 前端，另提供 Docker 镜像。
- **Docker 镜像预装多个版本的 `mysqldump` 和 PostgreSQL 客户端工具**，程序根据服务端版本自动选用匹配的版本。直接使用二进制时，由探测检查本机工具是否存在、版本是否匹配。〔用户决定：两种发布方式都提供〕
- 程序自身的数据（配置、任务、运行记录、托管密钥）保存在主控端本地。托管的仓库密钥和数据源凭据必须加密保存，不以明文落盘。
- **登录**：首次启动时引导设置唯一的管理员账号，需输入启动日志中打印的设置码。登录方式为密码，或已绑定的一个 OIDC 身份；绑定 OIDC 后可以关闭密码登录。未登录时所有页面和 API 都不可访问。
- **API 令牌**：管理员可以生成、查看最近使用时间、吊销 API 令牌。令牌只在生成时完整显示一次；吊销后立即失效。

## 信息架构

侧栏导航依次为：**概览、任务、快照与恢复、数据源、存储**，然后是“系统”分组下的**通知、设置**。

- 页面标题、按钮、状态文案都要支持中英文切换。数字、地址、耗时统一用等宽字体。
- 所有颜色来自设计变量，深色和浅色主题下文字对比度均须达到 WCAG AA（普通文字 ≥ 4.5:1，图标 ≥ 3:1）。
- 按钮、实心标签这类“绿底上放文字”的地方，统一用深一档的 `primary` 绿配白字；品牌薄荷绿只用于强调数字、图表、标识等装饰性位置。

## 概览

- 显示四个统计：受保护的数据源数量、24 小时成功率、存储占用（去重后，附节省比例）、下一次运行时间及对应任务。
- 显示最近运行列表，可按“全部 / 备份 / 同步 / 失败”筛选，状态分为：成功、运行中（带进度）、失败、等待中、实时同步。
- 显示近 14 天的运行柱状图（成功和失败分开统计），以及每个存储的用量。
- 数据为空时要有引导，引导用户去添加数据源和存储；数据加载失败时要显示错误状态，不能出现空白页。（设计稿尚未绘制）

## 数据源与能力探测

数据源是一份可复用的连接配置，包括地址、端口、凭据、TLS，需要时还有 SSH 跳板；服务器文件类型则是一台 SSH 可达的主机加上目录。同步任务的目的地同样从数据源中选择。

**探测时机**：保存数据源时自动执行一次，也可以在数据源详情页、新建任务第 2 步手动重新探测。结果带时间戳并缓存。

**探测结果分三档**：可用、可用但有风险、不可用。“可用但有风险”和“不可用”都必须说明原因。凡是可以修复的项，都要给出可直接复制执行的修复方法（SQL、配置项或命令）。

**各类型的探测项**：

| 类型 | 探测项 |
|---|---|
| MySQL | 版本；`log_bin` 是否开启；`binlog_format` 是否为 ROW；是否开启 GTID；binlog 保留时长；账号是否有 REPLICATION SLAVE / CLIENT 权限；是否存在非 InnoDB 表（有则提示全量时需要锁表）；主控端 `mysqldump` 版本是否与服务端匹配 |
| PostgreSQL | 版本；`wal_level`；`max_wal_senders`；复制槽是否可用；账号是否有 REPLICATION 属性；主控端 `pg_dump` 的大版本是否不低于服务端 |
| MongoDB | 副本集还是单机；oplog 大小，以及据此估算“增量能容忍多长时间的中断”；账号是否有 backup 角色 |
| Redis | 是否允许 PSYNC；是否为集群模式；内存占用 |
| Kafka | 协议版本；topic 与消费组的 ACL |
| 服务器文件 | SSH 可达；CPU 架构（amd64 / arm64）；临时目录是否允许执行程序；是否可以免密 sudo；目标路径所在文件系统，是否位于 LVM 卷，卷组剩余空间多少；文件数量与总大小估算 |

**失败处理**：探测过程中连接失败或超时，结果显示为“无法探测”，并附上错误信息，不能用上一次的缓存结果冒充本次成功。

## 任务与新建向导

任务分为**备份**和**同步**两种类型。

新建向导共 5 步：**类型与数据源 → 内容与方式 → 目的地 → 计划与保留 → 确认**。只有第 2 步随数据源类型变化，其余四步所有类型一致。已完成的步骤可以点击返回修改。

1. **类型与数据源**：选择备份或同步，再从数据源列表中选择一个，列表中显示每个数据源的连接状态；选中后，在该行显示探测摘要，例如“6 项通过 · 1 项提醒”。（设计稿尚未绘制）
2. **内容与方式**：
   - 顶部是探测面板
   - 然后是备份范围、备份方式、“<类型> 选项”区块；少用的选项折叠在“高级选项”里
   - 探测判定不可用的方式要灰掉并说明原因；对该类型本来就不存在的方式（例如 Redis 的增量）直接不显示
3. **目的地**：选择存储（本地目录或 S3），设置路径前缀（下方实时显示最终的完整路径），设置压缩算法（不压缩 / gzip / zstd，默认 zstd）。加密是存储本身的属性，这里只显示当前存储的加密状态，不能单独修改。
4. **计划与保留**：
   - 频率：每小时 / 每天 / 每周 / 自定义 Cron，并显示时区和接下来三次的执行时间
   - 全量周期：仅在第 2 步选择了“全量 + 增量”时出现
   - 保留策略：按天、周、月三档设置，并显示长期占用估算
   - 失败重试次数与间隔、超时时长
   - 通知条件：“失败时”“超时未运行”默认开启，“成功时”默认关闭
5. **确认**：任务名称可以修改；四组摘要各带一个“修改”入口；创建后可以选择立即执行一次（默认）或等待下一次计划执行；底部显示首次全量的体积和耗时估算。

**不合法的输入不能进入下一步**，错误信息显示在对应字段旁边，例如 Cron 表达式写错、路径前缀非法、保留数量为 0。

## 各引擎的全量与增量

| 类型 | 全量 | 增量 | 恢复粒度 |
|---|---|---|---|
| MySQL | 官方 `mysqldump`，使用 `--single-transaction`，同时记录 binlog 位点或 GTID | 纯 Go 持续接收 binlog〔已核实可行〕 | 开启增量后可恢复到任意时间点，否则只能恢复到某个快照 |
| PostgreSQL 逻辑模式 | 官方 `pg_dump`，可以按库选择 | 不支持 | 只能恢复到某个快照 |
| PostgreSQL 物理模式 | 纯 Go 物理基础备份（覆盖整个集群）〔已核实可行〕 | 纯 Go 持续接收 WAL〔已核实可行〕 | 任意时间点；恢复时 PG 大版本必须一致 |
| MongoDB | 官方 mongo-tools 的 `mongodump`，作为 Go 库嵌入（Apache-2.0〔已核实〕），不需要安装〔用户决定〕 | 读取 oplog，仅副本集可用 | 副本集可恢复到任意时间点，单机只能恢复到某个快照 |
| Redis | 通过复制协议拉取 RDB | 不支持（界面上不显示增量选项） | 只能恢复到某个快照 |
| Kafka | 无全量概念 | 按 offset 持续续传 | 重放到目标 |
| 服务器文件 | 首次全量 | 按上次快照的文件元信息比对变化，分块后只传缺失的块 | 恢复到某个快照，可恢复单个文件或目录 |

**全量与增量的衔接**：全量快照必须记录它对应的日志起点（binlog 位点或 GTID、WAL LSN、oplog 时间戳），增量从这个起点接续。如果日志出现断档（例如源库的 binlog 已被清理），该任务的状态必须标记为“增量中断”，并发出通知，下一次运行时自动转为全量。**不能在有断档的情况下继续报告成功。**

## 同步任务

同步是**单向**的：把源端的数据持续或定期复制到目标端。目标端从“数据源”中选择，而且必须与源端类型相同。同步不经过仓库，不保留历史版本。

各类型的同步方式〔用户决定〕：

| 类型 | 初始化 | 持续同步 | 触发方式 |
|---|---|---|---|
| MySQL → MySQL | 官方 `mysqldump` 导出后导入目标端 | 纯 Go 接收 binlog 并回放到目标端 | 持续 |
| PostgreSQL → PostgreSQL | 官方 `pg_dump` 导出后导入目标端 | 逻辑复制（pgoutput）解码后回放 | 持续 |
| MongoDB → MongoDB | `mongodump` 导出后导入目标端 | 持续读取 oplog 并回放（仅源端为副本集时可用） | 持续 |
| Redis → Redis | 拉取 RDB 后导入目标端 | 以副本身份持续接收命令流并回放 | 持续 |
| Kafka → Kafka | 按起始位置（最早 / 最新 / 指定时间）开始消费 | 持续消费并写入目标 topic，可选同步消费组 offset | 持续 |
| 目录 → 目录 | 源端和目标端各推送一个临时执行器，用 rsync 的差异算法做首次完整同步 | 按计划重复执行差异同步 | 定时 |

**目录同步的实现**：不依赖服务器上安装的 rsync 程序。rsync 协议由纯 Go 实现（`gokrazy/rsync`，BSD-3-Clause〔已核实〕）编进临时执行器，两端服务器都不需要安装任何东西。

**目录同步的传输路径，由用户在任务里选择**〔用户决定〕：
- **直连**：源端执行器直接连接目标端，要求源端能访问目标端。主控端为本次任务临时生成一次性凭据，任务结束即作废
- **经主控端中转**：两台服务器不需要互通，但流量要经过主控端
- 选择“直连”时，探测阶段检查源端能否访问目标端，不通则不能保存任务，并提示改用中转

**必须满足的要求**：

- **延迟可见**：持续同步的任务要在概览页和任务详情里显示当前延迟，例如“延迟 1.2s”。超过阈值时触发通知。
- **断点续传**：同步进程重启后，要从最后确认写入目标端的位置继续，不能重复回放，也不能跳过数据。
- **中断处理**：源端日志已被清理导致无法续传时，任务状态标为“同步中断”并通知，由用户决定是否重新初始化。不自动清空目标端。
- **目标端保护**：初始化前，如果目标端不是空的，必须明确提示并二次确认。
- **冲突**：目标端被其他程序写入导致回放失败时，任务暂停并显示出错的那条变更。v1 不做自动冲突解决。

## 服务器文件与临时执行器

**读取方式**：
- **直接读取**：边读边传，适合不常变动的文件
- **文件系统快照**：当前只支持 LVM。执行器先创建只读快照再从快照读取，结束后删除快照。只有位于 LVM 卷上的路径才走快照，其余路径按直接读取处理，界面上要逐条路径标注

**执行流程**：
1. 主控端通过 SSH 把与服务器架构匹配的 worker 程序推送到临时目录并运行
2. worker 以客户端身份，经 SSH 隧道连接主控端内嵌的 kopia 仓库服务
3. worker 在本地扫描、切块，只上传仓库中缺失的块
4. 结束后删除 worker 程序；如果创建过 LVM 快照，一并清理

**凭据**：worker 在任何时候都不持有存储凭据和仓库密钥。

**兜底**：临时目录不允许执行程序、或 CPU 架构不支持时，自动退回纯 SFTP 读取，并在任务详情里注明“使用了兜底方式，速度较慢”。

**失败处理**：worker 中途异常退出、SSH 断开、快照创建失败时，本次运行记为失败，已上传的数据块不形成快照。同时尽力清理 worker 程序和 LVM 快照；清理失败的，要在运行记录里列出残留物所在的路径。

**可选项**：排除规则、是否保留权限与属主、扩展属性、硬链接、是否跟随软链接。高级选项里有：前后置脚本、快照空间上限、传输限速、单文件大小上限。

## 存储、仓库与加密

- 每个存储对应一个 kopia 仓库，后端为本地目录或 S3 兼容存储。每个任务在仓库里用路径前缀区分，快照打上标签：任务 ID、全量或增量、日志位点。
- **首次启用加密**：在添加存储时弹出“设置加密密钥”。默认由系统生成随机密钥，提供复制、下载密钥文件、重新生成操作，并显示密钥指纹；也可以切换为自设密码。用户必须勾选“我已保存这把密钥，并明白丢失后数据无法恢复”，才能启用。
- **托管方式**：密钥加密后保存在主控端，用于定时任务和恢复。界面上明确告知：服务器损坏或被重装后，只有用户离线保存的那份密钥能解开备份。
- **遇到已有仓库**：目标位置已存在 kopia 仓库时，弹出“解锁已有备份仓库”，显示仓库的创建时间和快照数量，要求用户粘贴密钥或上传密钥文件。密钥错误时显示“密钥不正确”以及连续失败次数；不允许覆盖或删除已有仓库。
- **不锁定数据**：用户可以用 kopia 官方命令行加上自己保存的密钥，直接打开 OpsNap 的仓库恢复数据。产品文档须说明这一点。

## 快照与恢复

- 快照页列出各任务的快照，按任务、数据源、时间筛选。
- 恢复有两种方式：
  - **选快照恢复**：所有类型都支持
  - **按时间点恢复**：仅限开启了日志型增量的数据源（MySQL binlog、PG 物理模式、MongoDB 副本集），界面上显示可恢复的时间区间
- 恢复目标有三种：
  - **原数据源**
  - **另一个同类型数据源**
  - **导出为文件下载**：数据库类为官方工具格式的导出文件，服务器文件为打包后的所选文件或目录
- **恢复到原数据源**属于破坏性操作：必须二次确认，并要求输入数据源名称；默认先对原数据源做一次全量快照再覆盖，用户可以取消勾选。
- **PG 物理模式**的恢复会写入目标主机的数据目录，因此要求目标是一台可以 SSH 登录的主机，并且恢复期间该 PG 实例处于停止状态。界面上要在选择目标时说明这一点，不满足时不允许开始。
- 恢复过程显示进度，结果写入运行记录；失败时说明失败在哪一步，以及目标端当前处于什么状态（例如“已清空，尚未写入”）。
- 服务器文件支持只恢复单个文件或目录，可以恢复到原路径或另一个路径；目标文件已存在时，由用户选择覆盖、跳过或重命名。

## 通知

- 渠道：邮件、Webhook、飞书、钉钉、企业微信、Telegram〔用户决定〕。Slack 不在 v1 范围内。
- 每个渠道都要提供“发送测试消息”，并在界面上显示发送结果。
- 触发条件：任务失败；超时未运行（到了计划时间但没有执行）；耗时或体积明显异常；同步延迟超过阈值；存储空间快满；增量中断。
- 发出的通知都要留下事件记录，记录可以被标记为已处理。

## 不在本期范围

- 常驻 Agent 和“节点”页
- 云盘快照（依赖云厂商 API，恢复粒度只到整块磁盘）
- 需要在数据库主机本地执行的物理备份，例如 MySQL XtraBackup、Redis BGSAVE 拷文件。第二版可借助临时执行器实现
- ZFS / btrfs 原生块级增量：kopia 的分块去重已经覆盖了主要收益
- 让用户选择备份工具，例如 mydumper
- SFTP 作为存储后端
