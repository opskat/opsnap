# 文件任务的目录浏览

> Status: Approved
> Owner: opsnap 维护者
> Last updated: 2026-10-22

**Objective:** 给文件任务填目录时，管理员可以从服务器上逐层浏览并直接选中目录，不必凭空记住并手打绝对路径；选中的路径在保存前就能确认可读。

**Hard invariant:** 浏览是只读的：不创建、不修改、不删除服务器上的任何东西，也不产生任何凭据迁移。已有的「失败或不完整的导出不能记为成功的快照」不变——浏览只影响填表，不改变 rsync 与快照的既有行为。

## Problem

1. **文件任务只能手打路径，打错要到运行时才知道。** 现在「目录」是一串纯文本输入框（`frontend/src/pages/job-sections.tsx:244`），后端只校验字符串形状：以 `/` 开头、不含 `..`（`internal/model/entity/job_entity/job.go:305`）。路径不存在、拼错、指到别的机器上的目录，都要等备份跑起来、rsync 失败之后才暴露，且这次运行不留快照。
2. **测试连接完全不检查目录。** 文件任务的测试连接只建 SSH 链路并检查存储位置（`internal/service/job_svc/conn.go:151`），`addr` 直接置空（`conn.go:163`）。管理员点「测试连接」看到「全部通过」，但目录可能是错的。
3. **不知道目录里有什么。** 填 `/srv/www` 还是 `/srv/www/uploads`、要不要再多加一个 `/var/backups`，面板上没有任何依据。

## Actors and user stories

1. 作为**管理员**，我想在填目录时从服务器根目录往下点选，这样不用记路径也不会拼错。
2. 作为**管理员**，我想点选完就看到「这个目录读得到」，这样保存前就知道这次配对了。
3. 作为**管理员**，我想在权限不够时当场看到是哪个目录、为什么读不了，这样知道该去哪加权限。
4. 作为**管理员**，我想在测试连接时一次看到所有目录的问题，这样不用一条一条试。

## Design decisions

标记：〔用户〕用户已决定；〔核实〕已从代码核实；〔推荐〕经用户确认的推荐方案。

| # | 决策 | 依据与否决方案 |
|---|---|---|
| 1 | 只做**目录浏览**，不做 NFS 直连、不做容器内 FUSE 挂载、不新增「本机挂载」这类数据源位置〔用户〕 | NFS 无用户名密码，靠客户端 IP + uid 映射授权，省掉的只是宿主机一条 mount；而可用 Go NFS 客户端库不成熟（`vmware/go-nfs-client` 仓库已归档，NFSv4 只有 1 star 的实现），不挂载就直接丢掉 rsync 的增量能力。否决：自己维护 NFS 客户端 |
| 2 | 浏览走**已在用的 SSH 连接**（含代理链与指纹校验），经 SFTP 子系统逐层列目录〔推荐〕 | 复用 `sshconn` 已建立的链路与凭据体系，不新增凭据入口，也不需要服务器上有 rsync 或特定 shell。否决：执行 `ls` 解析文本（引号、空格、换行文件名都不可靠，且要拼 shell 命令）；否决：SFTP 直连（要另填一套地址和密码） |
| 2b | 用 `github.com/pkg/sftp` 作为 SFTP 客户端，经 `session.RequestSubsystem("sftp")` 挂在既有 SSH 会话上〔推荐〕 | 该库是 Go 生态里事实上的标准实现（rclone 等在用），BSD-2 许可，只依赖 `golang.org/x/crypto`（已在用）。估：新增一个直接依赖，`go mod tidy` 后进 `go.sum`。否决：自己实现 SFTP 协议；否决：远端执行 `find`/`ls` |
| 3 | 每次只列**一层**目录，前端按需向下点〔推荐〕 | 递归列举在大目录上会卡住，且列出来的东西管理员大多用不到。否决：一次递归返回整棵树 |
| 4 | 列表只含**目录**，不含文件，也不统计文件数与占用大小〔用户〕 | 备份对象是目录；文件数/大小要 `du` 递归，几 TB 目录上很慢，只是参考信息。否决：显示大小与文件数 |
| 5 | 路径输入框保持可编辑，浏览只是辅助填值〔推荐〕 | 已配好的任务、路径很长或系统自动生成的场景，手打更快。否决：把输入框改成只读、只能浏览选 |
| 6 | 保存时校验路径存在且是目录，不存在给字段错误〔推荐〕 | 与「字段错误显示在对应字段下方」的既有约定一致（`frontend/src/lib/jobs.ts` 的 `KNOWN_FIELDS`）。否决：只在测试连接里报 |
| 7 | 测试连接增加「目录可读」一项，逐条列出所有不可读的路径〔用户〕 | 与字段错误互补：字段错误在保存时立刻指出是哪一条，测试连接一次暴露全部问题并说明原因。否决：只留其中一个 |
| 8 | 路径不存在 / 不是目录 / 无读权限 归为**字段错误**，按既有规则组织在对应字段下，有这类错误时不能保存；服务器连不上不算字段错误（见 10） | 与数据库任务的字段错误一致，不引入两套规则。否决：目录读不到也允许保存（会直接得到一个必然失败的定时任务） |
| 9 | 保存时的目录校验**只做一次、失败不重试、超时短**，且校验不过不影响其他字段错误一次返回〔推荐〕 | 保存是交互动作，卡住比报错更糟。否决：保存时做完整递归检查 |
| 10 | 服务器暂时连不上时，保存**放行**并保留原有配置，不因为一次网络抖动就让人改不了任务〔推荐〕 | 与「连接测试没通过时可以保存，但要先确认一次」的既有产品判断一致（`docs/specs/2026-10-15-opsnap-v1.md` 表单交互）。否决：连不上就禁止保存 |
| 11 | 目录浏览失败（权限、不存在、非目录）各有明确文案，不使用笼统的「读取失败」〔推荐〕 | 管理员要据此决定去改权限还是改路径 |
| 12 | 浏览结果不缓存，也不写入任何表〔推荐〕 | 目录内容随时在变，缓存只会制造不一致；浏览是纯读操作，没有新实体 |
| 13 | 库列表与目录浏览共用「填好连接后读取」的交互范式，但**不共用接口**〔推荐〕 | 库列表是数据库协议探测（`job_svc/probe.go`），目录是 SFTP；混在一条接口里会让分支变复杂。否决：扩展 `/jobs/databases` 让它兼列目录 |
| 14 | 把 `paths` 从 `connectionFields` 里**移出**（`internal/service/job_svc/conn.go:24`）〔用户〕 | 该白名单的语义是「决定能否建立连接的字段」，路径是否填好与能否连上无关。不移出则路径框空着时测试连接会被「请至少填写一个要备份的路径」直接拦下（`11401`），新增的「目录可读」检查永远不会执行，第一次浏览也永远拿不到结果 |
| 15 | 「是不是目录」用 `Stat` 先判定，**不依赖 `ReadDir` 的错误码**〔核实〕 | `github.com/pkg/sftp` 的 `normaliseError`（`client.go:2231`）只映射 `EOF` / `NoSuchFile` / `PermissionDenied`，对普通文件执行 `opendir` 得到的是裸 `SSH_FX_FAILURE`，`errors.Is` 判定全部失效。因此 `not_dir` 必须由 `Stat().IsDir()` 得出 |
| 16 | 列举过程中的任何错误都**整层作废**，不返回半份列表〔核实〕 | `ReadDirContext` 在传输中途失败时会把已收到的条目连同错误一起返回（`client.go:379`）。把半份列表当完整列表展示，会让管理员以为目录里只有这些，从而漏备 |
| 17 | 符号链接目录在列表里**标出来**并在选择后提示〔核实〕 | 实测 rsync `--archive` 不跟随符号链接：源参数本身是链接时只同步一个链接（`ln -s real link` + `rsync -a --relative` 的结果是链接，不是内容）。但 SFTP 的 `opendir` 会跟随链接列出内容——浏览看到有内容、备份出来是空的，这是最容易误导人的不一致 |
| 18 | 浏览会刷新服务器的「最近连接 / 延迟」记录〔核实〕 | 浏览复用 `sshconn.Dial`，它成功后会 `RecordCheck` + `UpdateStatus`（`sshconn/server.go:69-71`）。这不算错——连接确实成功了，记录下来是对的；但不做额外处理，也不为浏览单独拆一条不记录状态的连接 |
| 19 | 条目上限 2000 是**返回后的截断**，不是读取时的止损〔核实〕 | `ReadDir` 会把整层读进内存才返回，没有分页入口；一个几十万条的目录层照样会把内存和时间吃满。因此 20 秒超时是主要止损手段，文案要写明「条目太多时可能超时，请直接填路径」 |

## 目录浏览

入口是「文件」任务「连接」卡片里的目录行：路径输入框右侧一个「浏览」按钮（参考 mockup：`.dev-kit/artifacts/2026-10-22-file-path-browser/mockups/`，仅作佐证，以本文为准）。

**前置条件：** 已选择服务器。没有选服务器时「浏览」按钮不可用，并说明要先选服务器。

**打开时：**

- 打开时停在当前输入框里的路径；输入框为空时停在 `/`。
- 输入框里的路径读不出来时**不静默跳走**，就在原地说明是哪一条路径、什么原因，并给出「上一级」「回到根目录」「重试」三个出口——管理员需要知道原来那条路径为什么不行，直接跳到 `/` 反而会以为是打开失败。
- 选择器顶部是可点的面包屑（`/ srv www uploads`），每段都能点击跳回该层。
- 中间是当前目录下的子目录列表，每项显示名称与修改时间，点击进入下一层；第一项是「上一级」，根目录下不显示。
- 指向其他目录的符号链接也列出来，但带一个「链接」标记；选中它时在该行下方提示「`<路径>` 是符号链接，rsync 只备份链接本身，不备份它指向的内容」（决策 17）。
- 名称含控制字符或不是合法 UTF-8 的条目仍然列出，但不可选，标注「名称含特殊字符，不能在面板里选，请直接填路径」——不静默隐藏，否则管理员会以为服务器上没有这个目录。
- 底部固定显示「将备份 `<当前路径>`（N 个子目录）」和「取消」「选择此目录」两个按钮。

**选择：**

- 点「选择此目录」把当前路径写回对应的输入框，并关闭选择器；该行下方出现一条「已确认可读，N 个子目录」的提示。
- 手改这一行的路径后，这条提示立即消失（它只描述浏览过的那次结果）。

**读取失败与边界：**

- 正在读取时显示「正在读取 `<路径>`…」，不显示空白区域；此时「选择此目录」不可用。
- 权限不足时：原地写「读不了 `<路径>`：登录用户没有读权限（Permission denied）。换一个目录，或给 `<服务器>` 上的登录用户加上读权限。」，并给一个退回上一层的按钮（有上一层时）或退回 `/` 的按钮。
- 目录不存在、或路径是文件而不是目录时：同样原地说明，并给退回入口。
- 目录里没有子目录时：写「这个目录下没有子目录。仍然可以选它——里面的文件会被备份。」，仍可选中。
- 单个目录的条目数超过 2000 条时只返回前 2000 条并提示「条目太多，只显示前 2000 个。可以直接在输入框里填完整路径。」。这条上限只能管住界面，管不住传输：整层内容在截断前已经传完，所以真正超时的时候会按超时处理（决策 19）。
- 一次列目录的超时为 20 秒；超时按「服务器响应超时」报错，不重试。
- 列举中途失败时这一层整体按失败处理，不展示已收到的那部分（决策 16）。
- SSH 链路本身的失败（某一跳超时、认证失败、指纹不符）沿用服务器测试连接的既有原因分类与文案，写在选择器里。

**可访问性：**

- 选择器是模态对话框，用键盘可以完成全部操作：Tab 在面包屑、列表项和按钮之间移动，Enter 进入目录，Esc 关闭且不改变输入框。
- 列表项是按钮而不是可点击的行，有可见的焦点样式。
- 「上一级」有可读标签；只有图标的刷新按钮带 `aria-label`。

## 保存与测试连接时的校验

**保存时的路径校验：**

- 对文件任务的每一条路径，经服务器确认它是一个存在的目录。
- 不满足时给出字段错误 `paths`，文案写明是哪一条路径、什么原因（不存在 / 不是目录 / 没有读权限）。
- 服务器连不上（超时、认证失败、指纹不符）时**不报路径错误**，保存继续，并在成功提示里说明「没能确认目录是否存在，运行时还会检查」。这样网络抖动不会挡住管理员保存配置。
- 校验总时限 20 秒；超时按「连不上」处理，同样放行保存。

**测试连接新增一项：**

- 检查项 key 为 `paths`，标签「目录可读」，排在「SSH 链路可达」之后、「存储位置可达、已挂载」之前。
- 逐条检查所有路径：全部可读时通过，并写出「N 条路径都可读」；有不可读的时列出每条不可读的路径与原因。
- 判定「是不是目录」用 `Stat`，不看 `ReadDir` 的错误码（决策 15）。
- SSH 链路不通时这一项标记为已跳过，原因与既有检查项一致。

实现上复用 `Deps.DialSSH` 建立的同一条连接，不再第二次握手；整组路径检查共用一个 20 秒超时。

**接口：**

新增 `POST /api/v1/jobs/paths`，请求体与 `/jobs/databases` 字段一致（携带完整任务配置，`id` 非 0 时表示编辑中的已保存任务），额外一个字段：

- `path`：要列哪一层；为空表示 `/`。

响应：

- `ok`、`path`（规范化后的目录）、`list`（每项含 `name`、`mtime`、`symlink`，按名称排序）、`truncated`；
- 失败不是接口错误，与 `/jobs/databases` 一致：`ok=false` 加 `reason`、`reason_label`、`message`，面板原地展示并提供重试；
- `reason` 取值：SSH 链路失败时沿用服务器的原因分类（`timeout`、`auth_failed`、`fingerprint_mismatch` 等）；SFTP 层面为 `not_found`、`not_dir`、`permission`、`sftp_unavailable`、`timeout`、`failed`。

`path` 字段只接受空串或绝对路径，不接受含 `..` 或 NUL 的值；这类输入归为字段错误（`11401`，字段名 `path`），不进入 SFTP。

不新增错误码：浏览失败一律走 `ok=false` 的响应形状（同 `/jobs/databases`），只有参数形状错误用既有的 `JobFieldInvalid`。

**与既有代码的连接（实现约束，已核实）：**

- `paths` 从 `connectionFields` 移出（决策 14），否则路径框空着时 `prepareConn` 直接 `11401`，浏览与新增检查项都不可达。改动后测试连接在路径未填时也能跑——这是修正，不是退化：测试连接本来就该允许在配置未填完时执行。
- `Tunnel`（`internal/service/job_svc/job.go:70`）只返回本机可达地址，拿不到 `*ssh.Client`。`Deps` 新增 `OpenFS func(ctx, serverID int64) (Browser, func(), error)`；浏览、保存校验、测试连接的「目录可读」都走它，开一条 SFTP 会话。
- 测试连接里「SSH 链路可达」仍走 `Tunnel`，因此一次测试连接会建两条 SSH 连接（一条查链路，一条开 SFTP）。这是本轮接受的代价：把两者合成一条要改 `Tunnel` 的返回类型，影响数据库任务的分支，改动面大于收益。

**兼容性：**

- 浏览依赖服务器开着 SFTP 子系统（OpenSSH 默认 `Subsystem sftp`）。子系统没有开启时，「浏览」打不开，选择器里写明「这台服务器没有开启 SFTP，不能浏览目录；可以直接在输入框里填完整路径」，手填与保存不受影响。
- 目录浏览是可选辅助：服务器上跑着受限 shell、或者 SFTP 被拆掉的机器，任务仍然可以正常创建和运行。

**不做的事（明确边界）：**

- 不改文件任务的执行链路：仍是 rsync 同步到本机镜像再生成快照（`internal/service/run_svc/engine.go:405`）。
- 不改排除规则的语法与语义。
- 不为数据库任务的路径（存储位置路径、SSH 私钥路径等）提供浏览。

## Out of scope

- NFS、SMB 的直接读取（不经宿主机挂载）与容器内 FUSE 挂载；需要时另立 spec。
- 目录内容的递归预览、文件大小与文件数统计、按名称搜索目录。
- 在浏览里创建目录、删除目录或修改权限。
- 文件任务的「保存并运行」前强制跑一次完整的可读性扫描。
