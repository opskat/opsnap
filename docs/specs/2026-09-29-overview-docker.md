# 概览页、Docker 镜像与按服务端版本选择导出工具

> Status: Approved
> Owner: OpsNap 产品负责人
> Last updated: 2026-09-29

**Objective:** 管理员打开概览，能一眼看到受保护的数据源、最近 24 小时的成功率、存储占用、下一次运行、最近运行、近 14 天趋势和每个存储的用量；什么都还没配置时，概览引导他完成第一次备份。同时，OpsNap 提供每日构建的 Docker 镜像。镜像预装多个版本的导出工具，程序按数据源的服务端版本自动选用合适的版本。

**Hard invariant:**

1. **概览上的数字与任务页、存储页一致。** 同一时刻，概览上的运行状态、快照数和存储占用，与任务列表、任务详情、存储列表显示的值来自同一份记录，不能各算各的。
2. **有不低于服务端版本的工具时，不选更老的工具。** 自动选择只会在“没有不低于服务端的版本”时退而选择较老的版本，并且此时探测和运行日志都要说明。
3. **镜像不带任何秘密和出厂密钥。** 主密钥、元数据库只在第一次启动时生成在挂载的数据目录里；镜像和 nightly 流水线的日志里没有任何凭据。

标记说明：〔已核实〕= 查证过源码或官方资料；〔用户决定〕= 本轮讨论中用户已确认；〔默认〕= 按常规做法先定、用户已认可设计。

## 问题

1. **概览页只有系统状态。** 侧栏第一项「概览」目前只显示版本号和元数据库状态〔已核实，main 3dce01a，`frontend/src/pages/OverviewPage.tsx`〕。v1 spec「概览」要求的统计、最近运行、趋势和存储用量都没有。
2. **没有 Docker 镜像。** 仓库里只有测试环境的 compose 文件，没有镜像的构建文件，也没有发布流程〔已核实，`deploy/` 下只有 `test/`；`.github/workflows/` 只有 `ci.yml`〕。v1 spec 决策 16 要求同时提供镜像和单二进制。
3. **导出工具只能有一个版本。** 主控端找 `mysqldump`、`pg_dump` 时，先在 PATH 里找，找不到再到配置项 `tools.dir` 里找，每种工具只取第一个〔已核实，`internal/pkg/probe/tools.go` 的 `ToolPath`〕。备份多个不同版本的服务端时，只能手动切换工具。

## 角色与用户故事

1. 作为**管理员**，我想每天早上打开概览，就知道昨晚的备份有没有失败、存储还剩多少空间。
2. 作为**第一次使用的管理员**，我想在概览上看到接下来该做什么，一步步完成第一次备份。
3. 作为**运维**，我想用 `docker run` 一条命令跑起 OpsNap，不用自己装 mysqldump 和 pg_dump，也不用管服务端是什么版本。
4. 作为**直接运行二进制的运维**，我想在 `tools.dir` 下放几个版本的客户端，让 OpsNap 自己挑。

## 设计决策

| # | 决策 | 依据与被否决的方案 |
|---|---|---|
| 1 | 本轮做不了的入口显示但禁用，标“后续版本支持”：顶栏的搜索框、“恢复数据”按钮，最近运行的“同步”筛选〔用户决定〕 | 与向导里的禁用项一致，用户能提前知道这些会有。否决：隐藏搜索（设计稿里有，保留占位）；三项都隐藏 |
| 2 | 运行中的运行不显示百分比，显示已运行时长和已导出的数据量〔用户决定〕 | 运行中只知道已导出多少，不知道总量；向导的源数据量估算与导出量不是一回事，算出的百分比会超过 100% 或停住。否决：按估算显示百分比 |
| 3 | 存储用量按类型显示：都显示仓库实际占用和快照数；本地目录另外显示所在磁盘的“已用 / 总量”进度条和剩余空间；S3 不画进度条〔用户决定〕 | S3 没有容量上限的概念，本地磁盘满了会让备份失败，值得提前看到。否决：统一只显示占用；按最大者画相对进度条（会被误读为容量） |
| 4 | “受保护的数据源”指：至少被一个已启用的任务引用，且这个任务至少成功过一次、有可恢复的快照〔用户决定〕 | 只被引用而从未成功，数据其实没有保护。否决：只看是否被已启用任务引用；只看仓库里有没有快照 |
| 5 | 概览的空状态、首次加载失败和本轮完整概览，按新画的三张设计稿〔用户决定〕 | 原设计稿没有空状态和错误状态 |
| 6 | 概览的默认规则：24 小时成功率不计跳过和取消；最近运行显示最近 20 条；14 天图按浏览器时区分天；每 30 秒自动刷新；没有任何任务时显示引导〔默认，用户已认可设计〕 | 跳过和取消不是“备份失败”，计入会误报；20 条与设计稿一屏的量一致 |
| 7 | 镜像预装仍在维护的版本：MySQL 官方 `mysqldump` 8.0、8.4 和构建时最新的 9.x；PostgreSQL 客户端 14–18；MariaDB 服务端用 Debian 的 `mariadb-dump`。MySQL 5.7 服务端用 8.0 的 `mysqldump`〔用户决定〕 | 覆盖常见线上版本，镜像约 400–500 MB。否决：再装 5.7 客户端（构建要下载约 700 MB 的官方包）；每种只装最新一版（依赖向下兼容，老服务端会出小问题） |
| 8 | 按服务端版本选工具的规则同样适用于直接运行二进制的用户：`tools.dir` 下按约定放版本子目录即可；没有子目录时行为不变〔用户决定〕 | 镜像只是预先填好了这个目录，两种发布方式行为一致。否决：只在镜像里自动选 |
| 9 | 镜像每日构建 nightly，推到 `ghcr.io/opskat/opsnap:nightly` 与 `:nightly-<UTC 日期>`；按版本号发布正式镜像留到 v1〔用户决定：参考 katch 的 nightly 流程〕 | 能尽早拿到可用的镜像，又不占用 `latest` 与版本号。否决：只提供构建、不推送；每次合并都推送 |
| 10 | 容器内 OpsNap 以 root 运行〔用户决定〕 | 挂入任何宿主机目录作“本地目录”存储都能直接写，上手最简单。否决：非 root（需要用户处理挂载目录的归属） |
| 11 | 自动选工具的真实验收在 docker.internal 临时起 MySQL 5.7、8.4、MariaDB、PostgreSQL 14 与 18 的容器，用完删除；nightly 发布在合并前只验构建，合并后手动触发一次确认〔用户决定〕 | 测试环境长期只有 MySQL 8.0 和 PostgreSQL 16；定时与手动触发都要求工作流已在 main 上 |

## 概览

### 页头

- 标题“概览”，副标题“所有备份任务 · 最近 24 小时”。
- 右侧依次是：
  - 搜索框：禁用，占位文字“搜索 · 后续版本支持”；
  - “恢复数据”按钮：禁用，悬停提示“后续版本支持”；
  - “新建任务”按钮：进入新建向导。

### 四个统计

每个统计显示名称、主数值和一行说明。

1. **受保护数据源**：按决策 4 计数。说明按类型列出数量，如“MySQL 3 · PostgreSQL 2”。为 0 时说明为“还没有被任务备份的数据源”。
2. **24h 成功率**：
   - 统计开始时间在最近 24 小时内、已经结束的运行，成功率 = 成功 ÷（成功 + 失败）。跳过和取消的不计入。
   - 说明为“N 次运行 · M 次失败”，N 是成功与失败的次数之和。
   - 没有可计入的运行时，主数值为“—”，说明为“最近 24 小时没有运行”。
3. **存储占用**：
   - 所有存储的仓库实际占用之和（去重、压缩之后）。
   - 说明为“去重压缩后 · 节省 X%”，X = 1 − 占用 ÷ 仓库中快照的原始总大小。
   - 有存储读不到用量时，总和不含它，说明改为“有 N 个存储无法读取”。
   - 没有存储时为“0 B”，说明“还没有存储”。
4. **下一次运行**：
   - 已启用任务中最早的下一次计划时间，按浏览器时区显示。不是今天时带上日期。
   - 说明为“<任务名> · N 分钟后”（或“N 小时后”“明天”）。
   - 没有已启用的任务时为“—”，说明“还没有启用的任务”。

### 最近运行

- 显示所有任务中最近的 20 条运行，按触发时间倒序，包括等待中、运行中、跳过和取消的运行。
- **筛选**：
  - 全部；
  - 备份；
  - 同步：禁用，悬停提示“后续版本支持”；
  - “失败 N”：N 为最近 24 小时的失败次数，选中后显示最近 20 条失败的运行。
- **每行的列**：
  - 任务：引擎缩写（MY / PG）、任务名称、数据源地址；
  - 类型：本轮都是“备份”；
  - 状态：成功、运行中、失败、等待中、已跳过、已取消；
  - 耗时：已结束的显示总耗时，运行中的显示已运行时长；
  - 大小：成功的显示导出量，运行中的显示已导出量，其余为“—”；
  - 时间：开始时间。1 分钟内显示“刚刚”，当天显示“时:分”，更早的显示“月-日 时:分”。
- 点击一行进入该任务的详情页。
- 有任务但还没有任何运行时，列表处显示“还没有运行记录”。

### 14 天运行

- 最近 14 天（含今天）每天一根柱，按浏览器时区分天，成功与失败分开叠放。跳过与取消不计入。
- 悬停一根柱时显示当天的日期、成功次数和失败次数。
- 横轴两端标注第一天的日期和“今天”。
- 14 天都没有运行时，柱子为空，并注明“最近 14 天没有运行”。

### 存储目标

- 每个存储一行：名称、类型、仓库实际占用和快照数。
- **本地目录**：另外显示所在磁盘的“已用 / 总量”进度条，以及路径和剩余空间。
- **S3**：显示存储位置，不画进度条。
- **仓库用量的更新时机**：在每次运行、仓库维护或测试连接之后更新。概览显示最近一次读到的值，刷新概览本身不重新打开仓库。本地磁盘的总量与剩余在每次刷新时读取。
- **状态不是“正常”，或读不到用量的存储**：占用显示“—”，下方用错误色写出原因，例如“无法连接：目标位置不是 kopia 仓库”。
- 没有存储时，这一块显示“还没有存储”和“添加存储”链接。

### 空状态

- 一个任务都没有时，四个统计照常显示（为 0 或“—”）。最近运行、14 天运行和存储目标的位置，换成“开始第一次备份”引导。
- **引导共三步，按当前数据显示是否完成**：
  1. 添加数据源：已有数据源时打勾，并注明“已有 N 个数据源”，按钮“查看数据源”；没有时按钮“添加数据源”。
  2. 添加存储：规则同上，按钮“查看存储”或“添加存储”。
  3. 新建任务：前两步都完成之前，按钮禁用，并注明“需要先完成前两步”；完成后按钮可用，进入新建向导。
- 有了任何任务（不论是否运行过）之后，显示完整概览。

### 刷新与错误

- 概览打开期间每 30 秒自动刷新，不重新加载页面；浏览器标签页不可见时暂停，回到页面时立即刷新一次。
- **首次加载失败**：统计和各区块的位置显示错误原因和“重试”，不出现空白页。
- **已有数据后刷新失败**：保留已显示的数据，页面上方显示错误原因和“重试”，之后照常继续自动刷新。
- **单个存储读不到用量**：只影响那一行和“存储占用”的说明，见上文。

## 按服务端版本选择导出工具

### 目录约定

`tools.dir` 下可以放多个版本的客户端，每个版本一个子目录，工具放在子目录的 `bin/` 下：

| 子目录 | 用于 | 其中的工具 |
|---|---|---|
| `mysql-<主>.<次>`，如 `mysql-8.0`、`mysql-8.4`、`mysql-9.4` | MySQL 服务端 | `mysqldump` |
| `postgresql-<主>`，如 `postgresql-16` | PostgreSQL 服务端 | `pg_dump`、`pg_dumpall` |
| `mariadb` | MariaDB 服务端 | `mariadb-dump`（或 `mysqldump`） |

### 选择规则

- **某种工具在 `tools.dir` 下有版本子目录时**：
  - 在这些子目录中，选“不低于服务端版本的最低版本”。MySQL 按主次版本比较，PostgreSQL 按主版本比较。
  - 没有不低于服务端的版本时，选已装的最高版本。探测和运行照现有规则处理：
    - MySQL 工具较老时，探测为“有风险”，照常导出；
    - PostgreSQL 工具较老时，探测为“不可用”，运行失败在准备步骤。
  - 服务端是 MariaDB（服务端版本文本中含 MariaDB）时，使用 `mariadb` 子目录。没有这个子目录时，按 MySQL 的规则选。
- **没有版本子目录时**：行为与现在相同，先在 PATH 中找，再到 `tools.dir` 中找。
- **MySQL 5.7 服务端**：用 8.0 的 `mysqldump` 必须能成功备份，导出内容能导入空库并与源数据一致。
  - 数据源为“优先加密”时，TLS 握手失败（如官方 `mysql:5.7` 镜像只提供 OpsNap 不支持的 DHE 密码套件）改用不加密连接重试一次，与 PostgreSQL 一致；连接测试与探测照实显示未加密。其余四档不变，“必须加密”及以上握手失败仍报错；`mysqldump` 的 `--ssl-mode` 不变〔用户决定〕
- 能力探测的“主控端工具”项和运行日志的“导出工具”行，都写出实际选用的工具路径与版本，例如“导出工具 mysqldump：/opt/opsnap/tools/mysql-8.4/bin/mysqldump（8.4.6）”。

## Docker 镜像

### 内容

- 基于 Debian 稳定版的精简镜像，支持 `linux/amd64` 与 `linux/arm64`。
- 包含 OpsNap 单二进制（内嵌前端与 kopia）、CA 证书和时区数据。
- 预装的导出工具放在 `/opt/opsnap/tools`，按上文的目录约定：
  - `mysql-8.0`、`mysql-8.4`，以及构建时最新的 `mysql-9.x`，都是 MySQL 官方二进制；
  - `postgresql-14` 到 `postgresql-18`，来自 PostgreSQL 官方 apt 源；
  - `mariadb`，来自 Debian 的 MariaDB 客户端。

### 运行

- 默认监听 `0.0.0.0:8210`。
- 数据目录为 `/data`，存放元数据库、主密钥 `master.key` 和日志，应挂载为卷。
- 镜像内置默认配置，其中 `tools.dir` 指向 `/opt/opsnap/tools`。用户可以挂载自己的配置文件替换。
- 以 root 运行（决策 10）。“本地目录”存储需要用户把宿主机目录挂入容器。
- 第一次启动时，设置码打印在容器日志里（`docker logs` 可见）。之后的首次设置流程与二进制相同。
- 带健康检查，调用 `/api/v1/system/health`。
- 界面显示的版本号为 `nightly-<UTC 日期>`，以及对应提交的短号。
- 仓库文档给出 `docker run` 和 docker compose 两种示例，并说明三件事：
  - 数据卷里的 `master.key` 丢失后，已保存的凭据无法解密，要一起备份；
  - 如何挂载“本地目录”存储；
  - 如何换用自己的配置。

### nightly 构建

- 每天 18:00 UTC（北京时间 02:00），把 main 合并进 `nightly` 分支，再构建并推送镜像。
- 合并冲突时停下，`nightly` 保持原样，工作流报错。
- 定时或手动触发时，`nightly` 头部已经发布过就跳过，不重复构建。
  - 仓库里的引用 `refs/nightly/published` 指向最近一次发布成功的提交；只有 `nightly` 头部等于它时才跳过，引用不存在视为没有发布过。被取消或发布失败的那次运行，它的提交会由下一次运行测试并发布〔用户决定〕。
  - 每次运行从头到尾只测试和构建同一个提交，镜像显示的日期和提交短号都对应它。推送镜像标签前，如果 `nightly` 已经指向更新的提交，这次运行不推标签、不移动 `refs/nightly/published`，运行摘要写明“已被新提交取代”和两个提交号；`nightly` 标签不会退回到旧提交〔用户决定〕。
- 有人直接推送 `nightly` 分支时也构建一次，并支持手动触发。
- 推送前先跑测试，失败则不推送。
- amd64 与 arm64 在各自架构的 runner 上原生构建，再合成一个多架构清单，打 `nightly` 与 `nightly-<UTC 日期>` 两个标签。
- 不打 `latest`，也不创建 GitHub Release。
- **PR 上的 CI**：构建两种架构的镜像但不推送，并在镜像里运行一次冒烟检查。检查内容：服务能启动并通过健康检查；每个预装工具都能执行并报出版本。

## 界面

- 概览按三张设计稿实现。所有文案提供中文与英文，深色与浅色主题都要可用，颜色与字号只使用设计变量。数字、时间、大小、路径用等宽字体。
- 禁用的入口可以通过键盘聚焦，并能读出“后续版本支持”。
- 统计、列表与柱状图在加载中显示占位，不闪空白。

## 权限

- 浏览器会话与 API 令牌都可以读取概览数据〔默认，与任务一致〕。
